## 0.3. Правила применения статусов

1. Статус ставится только по доказательству: тест, файл:строка, отчёт гейта. «Работает» без доказательства — не статус.
2. `[ГОТОВО]` = есть регрессионный тест и он зелёный на HEAD. Если тест только на happy-path — это `[ЧАСТИЧНО]`.
3. `[ОТКЛОНЕНИЕ]` допустимо только как запись в §15 с решением. Молчаливое отклонение = дефект.
4. Изменение статуса — отдельным коммитом с обновлением CHANGELOG (репозиторий) и записью в §0.1/§16.
5. Формулировки требований v02 не переписываются задним числом; изменение фиксируется в §15/§19 и в §0.1.

## 1. Проблема

Большой отчёт (научная работа, ВКР, лабораторная, статья) — это не один файл, а связка: сырые данные → скрипты обработки → таблицы/графики/формулы → текст документа с перекрёстными ссылками, подписями, библиографией и правками руководителя. При длительной работе накапливается набор проблем, которые v01 обозначил тегами `#RDEсвязанностьобъектов`, `#RDEконтрольверсий`, `#RDEпометки`, `#RDEковорк`, `#RDEdocx`, `#RDEконтейнерфайла`.

**Формулировка v02.** Нужна среда, в которой:

1. **Связи данных формальны и проверяемы.** Изменение входного артефакта не «теряется»: среда знает, что устарело, умеет пересчитать ровно нужное и откатить неудачное обновление.
2. **Результаты остаются воспроизводимыми.** Для каждого сгенерированного файла известно, каким скриптом, с какими параметрами и окружением, из каких входов он получен.
3. **Документ собирается из объектов, а не копипастой.** Рисунки/таблицы/формулы/обозначения/константы/ссылки вставляются как ссылки на объекты проекта и обновляются централизованно; нумерация и подписи — по выбранным правилам (ГОСТ/вуз).
4. **Пометки и рецензирование не ломают документ.** Замечания руководителя приходят и уходят предсказуемо, с авторством, привязкой к месту текста и сохранением в Word-совместимом виде.
5. **Экспорт в `.docx` не разрушает данные.** Документ, собранный в RDE, выходит полноценным Word-файлом; ограничения (пагинация, поля) честно описаны и измеряются.
6. **Агент полезен на больших документах.** Он видит проект как API (MCP), получает точные ссылки на выделенный фрагмент/страницу PDF/выход артефакта, умеет править через принимаемые/отклоняемые предложения и не может молча сломать проект.
7. **Пользователь не заперт в приложении.** Проект — обычные файлы и git-репозиторий; `.doc.rde` — открываемый Word OOXML-пакет; внешние редакторы и скрипты работают.

## 2. Цель, продуктовая концепция, границы

**Продукт.** RDE (Research/Report Development Environment; рабочее название) — кроссплатформенное нативное приложение: Word-подобный редактор документов, развёрнутый в среду проектирования отчёта (project tree + артефакты/DAG + источники + заметки + документы + репозитории + встроенный AI-агент), с git-версионированием и экспортом в `.docx`/`.pdf`.

**Позиционирование.** Не «ещё один WYSIWYG», а «IDE для отчёта»: всё, что в Word делается копипастой и ручной сверкой, здесь — ссылки на объекты с автоматическим обновлением и проверкой целостности. Главный образец — MS Word; главный конкурент по функциям редактора — Word, главный «сосед по категории» — VS Code/САПР.

**Ядро ценности (must-have v1.0):**
- редактор документа уровня Word-подобного (форматирование, стили, таблицы, рисунки, формулы, поля, колонтитулы);
- артефакты с DAG, хешами, обновлением и откатом;
- сборка документа из объектов (вставки/подписи/ссылки/номера/библиография/константы);
- шаблоны ГОСТ 7.32-2017 + вузовские профили; рамка/штамп 2.105-2019 — v0.2;
- пометки/комментарии с авторами и Word-обменом;
- агент (DSH/ACP) + RDE MCP-сервер;
- git-версионирование и внутренние снапшоты;
- экспорт `.docx`/`.pdf` с измеримыми гейтами качества.

**Вне scope v1.0 (явно):**
- совместное редактирование в реальном времени (CRDT) — после v1.0 (фаза 3+);
- сервер и web-ревью — фаза 3 (архитектурный эскиз §8.8 сохранён);
- полноценная web-версия приложения (только read-only viewer в фазе 3+; в v1 web-сборки нет);
- плагинный маркетплейс/публичный plugin API (v1 — внутренняя регистрация команд и MCP как API);
- `.md.rde`-документ (v1: md — для заметок/импорта-экспорта; md-документ — фаза 2);
- MathType-экспорт с гарантией (только best-effort, §5.7.7);
- OCR в v1.0 (v0.2 как компонент установщика);
- мобильные ОС; точное воспроизведение пагинации Word (невозможно, §5.7.9).

**Критерий успеха продукта (продуктовая формулировка).** Пользователь проходит полный цикл «данные → артефакты → рисунки → документ по ГОСТ → ревью руководителя → финальный `.docx`» без ручной сверки номеров/ссылок и без потери данных при обмене с Word; при изменении входных данных обновление документа занимает секунды и обратимо.

## 3. Пользователи и сценарии

**3.1. Роли.**

| Роль | Описание | Ключевые задачи |
|---|---|---|
| Исследователь/студент (основной) | Пишет ВКР/статью/отчёт, владеет проектом | артефакты, документ, обмен с руководителем |
| Руководитель/рецензент | Не имеет RDE в v1; получает `.docx` и пишет комментарии в Word | оставить замечания, вернуть файл |
| Соавтор/коллега | В фазе 3 через сервер; в v1 — обмен файлами/git | пометки, правки |
| Агент (AI) | Внутренний (DSH) или внешний (MCP) | читать проект, править документ предложениями, запускать скрипты |
| Разработчик шаблонов | Настраивает ГОСТ-правила и вузовские профили | правила, стили, сборка шаблонов |

**3.2. Авторы (идентичности).** Локальные профили авторов: `ULID` + отображаемое имя + инициалы + опционально email + признак `human|agent|system`. Автор выбирается для документа/сессии; используется в комментариях (`w:author="Имя [rde:<ULID7>]"`), отслеживаемых изменениях, git-коммитах, записях provenance. Псевдонимы разрешены; ULID — ключ, имя — только отображение. Псевдонимы не должны становиться ключами [S10–S14].

**3.3. Ключевые сценарии (acceptance-ориентированные).**

- **С1. «Отчёт с графиками».** Пользователь создаёт проект, импортирует CSV как входной артефакт, пишет Python-скрипт артефакта-2 (статистика → CSV), артефакт-3 (график → SVG/PNG). В документ вставляет рисунок из артефакта-3, подпись с номером и обозначением величины; экспорт даёт `.docx`, где рисунок на месте, подпись «Рисунок 1 — …», номер обновляется при вставке второго рисунка.
- **С2. «Данные изменились».** Пользователь правит `run.py` артефакта-2 → статусы downstream-артефактов становятся `outdated` с причинами; «Обновить связанные» пересчитывает по топологическому порядку; неудачное обновление откатывается одной кнопкой; документ показывает «есть устаревшие вставки», обновление документа применяет новые значения и сохраняет транзакцию.
- **С3. «Ревью руководителя».** Экспорт `.docx` с комментариями и review-map → руководитель правит/комментирует в Word → импорт обратно: комментарии привязаны, новые — в очередь «сирот», правки тела — как suggested edits; пользователь принимает/отклоняет; исходный файл сохранён как неизменяемый снапшот.
- **С4. «Агент и большой PDF».** Пользователь открывает PDF источника (500+ страниц), выделяет фрагмент → «В чат»: в чате чип `rde://source/<id>?page=37&bbox=…`; агент читает текст/страницу, отвечает; на просьбу «перепиши раздел 2.3» создаёт предложения с диапазонами, пользователь принимает частично.
- **С5. «Сдал/защитил».** Финальный документ экспортируется в `.docx` и `.pdf`; fidelity-отчёт показывает отсутствие потерь данных; вывод «TOC/номера страниц пересчитает Word (F9)»; nothing silently lost.
- **С6. «Работа из файловой системы».** Пользователь открывает каталог проекта в проводнике/VS Code: манифесты читаемы, скрипты запускаются снаружи (`rde-cli run`), документ `.doc.rde` можно открыть копией в Word; git-история осмысленна.

## 4. Термины и модель мира

**4.1. Проект.** Каталог с `rde.toml` (+ `rde.lock`), объектами, шаблонами, экспортами и локальным служебным каталогом `.rde/` (кэш, индекс, журнал, снапшоты; в git не попадает). Проект — одновременно git-репозиторий (RDE инициализирует при необходимости) [S29,S30].

**4.2. Объект проекта.** Именованная сущность дерева: документ, артефакт, источник, заметка, репозиторий; плюс **служебные объекты** (скрыты по умолчанию): текстовый фрагмент (docx-совместимый rich text), константа/величина, **формула (служебный объект проекта: `objects/formulas/<id>/formula.toml` — LaTeX-источник, входы/фрагменты, политика нумерации, кэши OMML/SVG; одна формула переиспользуется в нескольких документах — [ADR-0005](adr/0005-formulas-and-values-as-project-objects.md))**, рисунок, подпись, запись библиографии, привязка вставки, экземпляр шаблона. У каждого объекта — стабильный `ULID` и манифест/метаданные в своей папке. Обозначение физической величины — **расширение константы** (R-ART-09: symbol/subscript/unit/display/style/format и значение-литерал ИЛИ `source` из выхода артефакта), отдельного типа верхнего уровня для него не вводится.

**4.3. Артефакт.** Объект с входами (группы зависимостей), скриптом генерации, параметрами, окружением и объявленными выходами. Подтипы: `compute` (скрипт), `data` (входные/статические данные), `constants` (набор типизированных значений без скрипта; доступен всем объектам и документу).

**4.4. Группа зависимостей.** Именованный набор входов артефакта с режимом:
- `hashed` — влияет на хеш действия (`act_key`) и на каскад устаревания;
- `ref` — только для provenance/UI («связано, но намеренно не пересчитывается»).
Семантика — как git tree (хешируемое содержимое) vs gitlink (пин на объект без каскада) [S29].

**4.5. Действие (action) артефакта.** `act_key = H(тип, schema_ver, in_hash, script_hash, params_hash, env_hash)`; результат — дерево выходов с `out_hash` (Merkle). Подробно §7.

**4.6. Обновление (update) / запуск (run).** Транзакция пересчёта: подготовка → выполнение → фиксация выходов в CAS → запись `runs/<run_id>/` (лог, provenance) → переключение текущих корней. Откат — переключение на предыдущие корни.

**4.7. Снапшот.** (а) внутренний immutable-снимок состояния объектов/документов для undo и краш-восстановления; (б) экспортный «пин» (шаринг/архив), защищающий данные от GC.

**4.8. Источник.** Объект-ресурс для ссылок/цитат: файлы, PDF, веб-страницы (локальный архив), внешние ссылки; содержит метаданные и запись библиографии.

**4.9. Документ.** Word-подобный объект с rich-текстом, стилями, полями, блоками и вставками. Рабочий файл — `.doc.rde` (OOXML-пакет WordCraft + RDE-части), плюс метаданные объекта. Источник истины — сам пакет + `rde:doc`-часть; RDE не держит второй модели документа «в отрыве» от `.doc.rde`.

**4.10. Вставка (insert).** Ссылка в документе на значение/ресурс: выход артефакта, константа/величина, рисунок, таблица, формула, запись библиографии, перекрёстная ссылка, подпись. Виды: inline-текст, блочный объект (рисунок/таблица/формула), поле Word. Вставки — управляемые объекты с ID и кэшем значения.

**4.11. Пометка (review mark) и автор.** Комментарий/замечание/исправление, привязанное к диапазону/блоку; автор, дата, статус (open/resolved), ответы. Канонический обмен — Word-комментарии (comments.xml + commentsExtended/commentsIds/people) + review-map в `rde:doc` [S10–S14].

**4.12. Шаблон.** Пакет правил оформления (стили, страница, подписи, таблицы, формулы, заголовки, списки, титул, содержание, библиография, единицы) + профиль стандарта + ресурсы. Композиция: каждое семейство блоков документа может ссылаться на правило из любого установленного стандарта; проект может копировать шаблон и переопределять параметры, не меняя глобальный [S25].

**4.13. Fidelity (точность экспорта).** Двумерное понятие: **полнота данных** (все части/элементы/поля сохранены) и **визуальное совпадение** (рендеринг/пагинация). Гарантии — разные (§5.7.9, §11).

Вкладки/сплиты/переносы панелей — `egui_dock` (`^0.36`, совместим с egui 0.36 WordCraft) [S18]. **`[ОТКЛОНЕНИЕ v03: кастомные панели без egui_dock — §15-1]`**

  - **2a (multi-window skeleton):** один eframe-App, несколько viewport'ов через `show_viewport_deferred` (дешёвле: immediate даёт vsync-связку и падение FPS), обязательный `Context::set_embed_viewports(false)`; собственный файл раскладки: `DockState` (serde) + геометрия окон (`ViewportBuilder::with_position/with_inner_size`, `ViewportCommand::SetMonitor`); на Wayland `outer_rect/outer_position` недоступны → сохраняем только размеры/порядок, позиции не обещаем.
  - **2b (команды вместо drag):** «Переместить вкладку в новое окно / в главное / на монитор N», контекстное меню вкладки.
  - **2c (спайк drag-tear-off):** общая drag-сессия на `egui::DragAndDrop` + глобальные координаты через `viewport().outer_rect` + один «принимающий» viewport; учесть, что egui-winit шлёт `PointerGone` при уходе курсора из окна и mouse-up может прийти только в исходное окно. Если спайк неубедителен — остаёмся на 2b.
  - Wayland: drag-tear-off не реализуем (winit не даёт позиций окон и глобального курсора) → команды и embedded-fallback. v1 — только внутренние «плавающие» панели (`egui_dock::Surface::Window` — это `egui::Window` внутри окна, не OS-окно).
- **R-UI-04.** Командная палитра (все команды с поиском), настраиваемые горячие клавиши, quick-open объектов, навигация «назад/вперёд», хлебные крошки в документе.
- **R-UI-05.** Нативное меню (muda) и диалоги (rfd) [S18]; drag&drop файлов в окно; тёмная/светлая тема; масштаб UI/документа; сохранение/восстановление раскладки.
- **R-UI-06.** Локализация интерфейса: ru/en в v1 (архитектура i18n — с первого дня); шрифты/ввод для кириллицы; bidi/сложные скрипты (арабский/индийские) — ограничение egui, документировать [S18].
- **R-UI-07 [РЕШЕНО, Q-02].** Доступность v1.0 — «минимум+»: полная клавиатурная доступность всех ключевых сценариев (навигация, команды, диалоги, дерево, вкладки), AccessKit-дерево панелей/списков/дерева, контрастная тема, масштаб интерфейса и шрифта; rich-редактор — базовые операции с клавиатуры (навигация, выделение, форматирование, поиск). ### 5.2. Дерево проекта

- **R-TREE-01 [РЕШЕНО].** Базовый набор типов фиксирован ядром: **Документ, Артефакт, Источник, Заметка, Репозиторий** + служебные объекты (скрыты по умолчанию, включаются режимом «показать служебные»). Пользовательские типы — только через будущий plugin API; в v1 расширяемость — данным (категории/группы), а не типам.
- **R-TREE-02 [РЕШЕНО].** Вид дерева настраивается: категории/группы/папки, фильтры по типу/статусу/автору, порядок, иконки, скрытие/показ типов и служебных объектов; несколько сохранённых представлений (по типам, по категориям, плоский список, «недавние»). Настройки — в `rde.toml` (переносимы с проектом).
- **R-TREE-03.** Операции: создать/переименовать/переместить/удалить (в корзину `.rde/trash/` с восстановлением), дублировать, «показать в проводнике», «показать в git», массовые операции; drag&drop в дереве и извне.
- **R-TREE-04.** Статусы в дереве: свежесть/устаревание артефакта (+причины), ошибки, незакоммиченные изменения, наличие пометок, «вставлен в документ».
- **R-TREE-05.** Виртуализация дерева/списков (десятки тысяч объектов без потери отзывчивости); поиск по имени/ID/метаданным; хлебные крошки.
- **R-TREE-06.** Обратные ссылки: «где используется» для любого объекта (артефакт→документы/артефакты; источник→ссылки/цитаты; шаблон→документы; постоянная→вставки).

### 5.3. Артефакты, DAG, обновление

- **R-ART-01.** Объект-артефакт: каталог `objects/artifacts/<id>/` с `artifact.toml` (манифест), `readme.md`, скриптом(ами), входными данными, каталогом выходов и собственным `.gitignore`. Манифест валидируется JSON Schema (генерируется из Rust `schemars`), редактируется в UI и текстом; комментарии/порядок сохраняются (`toml_edit`) [S30]. **`[ЧАСТИЧНО: toml_edit не подключён, §15-6]`**
- **R-ART-02.** Группы зависимостей `hashed`/`ref` (см. §4.4, §7). В одной группе — несколько входов; вход может указывать селектор выхода (`out/*.csv`) другого артефакта. Входы-«статичные» (файлы данных) — тоже группа (`hashed`, тип `file`).
- **R-ART-03 [РЕШЕНО].** Три режима реакции на изменения, выбираемые пользователем; дефолт — первый: **`[ЧАСТИЧНО: реализован только manual, §15-7]`**
  1) `manual` — только пометка «устарел» + явное обновление кнопкой (глобальный дефолт проекта);
  2) `watch` — авто-пересчёт при изменении входов/скрипта (debounce, очередь, отключается в настройках/на артефакт);
  3) `strict` — блокировка использования устаревших выходов до подтверждения/пересчёта (жёсткая проверка целостности).
  Режимы различаются на уровне артефакта и проекта; UI показывает выбранный режим и причину статуса.
- **R-ART-04.** Кнопки обновления: «обновить артефакт», «обновить связанные (downstream)», «обновить все артефакты проекта»; обновление идёт в топологическом порядке по `hashed`-рёбрам, с прогрессом по каждому действию, возможностью отмены (cancel) и лимитом параллелизма (настройка).
- **R-ART-05 [РЕШЕНО].** Транзакции и откат: каждое обновление — транзакция с журналом (`updates/<txid>.json`: prev/new roots, статусы, время, автор/инициатор, лог); «откатить обновление» (одно/все из транзакции/последнее) — O(1) переключение корней; окно отката (N последних обновлений и/или 7 дней — настройка); перед обновлением сохраняются снапшоты затронутых объектов; pins экспортов защищают от GC.
- **R-ART-06.** Целостность: проверка `act_key` + наличие блобов + `out_hash`; расхождение (ручная правка выходов, частичная запись) → статус `integrity_warning` с причинами и действиями «пересчитать/принять как есть/восстановить из CAS».
- **R-ART-07.** Циклы в `hashed`-графе запрещены на сохранении манифеста (DFS-раскраска; ошибка с указанием цикла). `ref`-рёбра не участвуют в топосортировке.
- **R-ART-08.** Provenance каждого запуска: `runs/<run_id>/provenance.json` в духе SLSA v1 (subject/out_hash, externalParameters, resolvedDependencies, RDE-расширения: git_commit+dirty, env_lock_digest, platform, script_hash, exit_code, log_digest, initiator) [S27].
- **R-ART-09 [РЕШЕНО].** «Константы» — подтип артефакта без скрипта: типизированные значения/величины с docx-совместимым форматированием (например, `R_н`: `R` курсив, `н` подстрочный). Доступны документам и другим артефактам; скрыты как служебные, если созданы шаблоном. **`[ГОТОВО: ADR-0005 P1, 2026-10-26]`** — `ConstantValue` расширен `symbol/subscript/format/source` (значение — литерал ИЛИ `rde://artifact/<id>[@<out_hash>]/<selector>`; `value` — обязательный кэш), `constant_hash` (`rde:const:1`) сохраняет совместимость хеша литералов, rich-вставки (`italic`/`italic-subscript`) и централизованная замена обозначения через вставки; доказательства — `rde-core/src/value_format.rs`, `rde-dag::{resolve_constant, constants_input_hash}`, тесты `rde-core`/`rde-dag`, `docs/schema/artifact.schema.json`.
- **R-ART-10.** Шаринг: экспорт отдельного документа/набора объектов в `.rde`-пакет (zip: `mimetype` первым несжатым, манифест, выбранные объекты, сабсет CAS, экспортированный `.docx`/`.pdf`, review-map) без всего проекта; импорт пакета как «архив/источник» или вливание объектов; пакет не зависит от git. **`[ЧАСТИЧНО: .rde.zip проекта ≠ R-ART-10 пакет, §19-6]`**
- **R-ART-11.** Диск/GC: content-addressed store, дедупликация, mark-and-sweep (корни: текущие корни + окно отката + pins + снапшоты); отчёт о занятом месте; ручная очистка кэша; предупреждение перед GC, ломающим pin.

### 5.4. Скрипты, окружения, исполнение

- **R-RUN-01 [РЕШЕНО].** Скрипт — любой исполняемый файл, объявленный в манифесте: `runtime = { kind, env, entry }`, где `kind ∈ {python, shell, node, r}` (WASM — позже, для расширений/линтеров, не для научных скриптов), `env` — ссылка на окружение проекта/артефакта. Python — первый класс; Node/R — по наличию окружения.
- **R-RUN-02 [РЕШЕНО].** Окружения: `uv` поставляется компонентом установщика и управляет per-project Python venv + `uv.lock`; R — `pixi`, Node — `pnpm`; версии интерпретаторов и lock-файлов фиксируются в `rde.lock`; hash окружения входит в `env_hash`. Пользователь может выбрать: системный интерпретатор / управляемое окружение.
- **R-RUN-03.** Установщик и ОС-интеграция [РЕШЕНО]: компоненты установки выбираются пользователем (ядро, PDF, OCR, Python/uv, Node, R, DSH); RDE «корректно» регистрирует выбранные инструменты в ОС (Windows: пользовательские переменные, PATH, ассоциации — отдельным опциональным компонентом с обратимым удалением; приоритет — собственное разрешение инструментов внутри RDE без глобального PATH). Подробно §8.10.
- **R-RUN-04.** Исполнение: отдельный рабочий каталог запуска; входы материализуются только для чтения (symlink/reflink/copy по ОС); каталог выходов; `cwd` = рабочий каталог; по завершении выходы хешируются и импортируются в CAS; файлы вне объявленных `outputs` — **ошибка**, а не предупреждение (защита от загрязнения графа).
- **R-RUN-05.** Управление процессом: timeout (манифест/настройка), отмена (SIGTERM → grace → SIGKILL, process group на POSIX, Job Object на Windows), стриминг stdout/stderr в лог с байтовыми смещениями (возможность переподключиться к логу), очередь запусков, лимиты параллелизма, индикатор ресурсов.
- **R-RUN-06.** Безопасность скриптов: первый запуск проекта/артефакта — явное согласие («проект доверенный», настройка), предупреждение о произвольном коде; сеть — **по умолчанию запрещена** для артефактов, включается декларативно (`network_allow = true` на артефакт/проект) с предупреждением [РЕШЕНО, Q-14]; best-effort без ОС-песочницы в v1; секреты — из keychain/переменных, не логируются; запуск от имени пользователя. Полная ОС-песочница — `[ОПЦИЯ]` фаза 2+ (WASI для плагинов, bwrap/landlock на Linux).
- **R-RUN-07.** Окружение/детерминизм: `env_hash` (runtime id, platform triple, lockfile digest, объявленные env-vars); уровень воспроизводимости «same machine» в v1, с честным индикатором; полный контейнер/nix — `[ОПЦИЯ]` позже.
- **R-RUN-08.** Логи: хранение `runs/<run_id>/stdout.log|stderr.log`; ретенция (N запусков/размер); поиск по логам; экспорт лога; панель «Запуски» артефакта со статусами/длительностью/инициатором.

### 5.5. Источники

- **R-SRC-01.** Объект-источник: файлы (любой формат), наборы файлов, PDF, markdown/txt/html/doc, внешние ссылки (URL), ссылки на локальный файл вне проекта; каталог `objects/sources/<id>/` с `source.toml`, файлами и (опционально) веб-архивом.
- **R-SRC-02 [РЕШЕНО].** Сохранение веб-страницы офлайн — встроенная функция: загрузка страницы **вместе с ассетами** в один HTML-файл через движок `monolith` (Rust CLI, CC0-1.0 — допустимая лицензия для бандла) [S23]; альтернативы (SingleFile — AGPL-3.0) отклонены [S24]. Сохраняются: исходный URL, время, хеш архива; опция «как PDF». **`[ОТКЛОНЕНИЕ v03: monolith не вендорен, §15-4]`**
- **R-SRC-03.** Метаданные: title, авторы, дата, издатель/venue, URL, retrieved_at, хеши, теги, заметка; для книги/статьи — поля библиографической записи по ГОСТ 7.0.100-2018 (свободные поля) + импорт BibTeX/RIS/CSL-JSON.
- **R-SRC-04.** Внешние ссылки: файл по абсолютному пути (read-only, отслеживание хеша/отсутствия), каталог-репозиторий (см. 5.8), URL (открытие в системном браузере + опциональный архив). Предупреждение «источник недоступен», без тихой подмены.
- **R-SRC-05.** Источник индексируется для поиска (извлечённый текст PDF/HTML; OCR — v0.2); используется в документе (цитата/ссылка) и агентом (ссылки на страницу/регион — R-AGT-03, R-AGT-04).
- **R-SRC-06.** Просмотр: PDF-вьюер (pdfium), HTML/markdown/txt — внутри вкладки; изображения; для сканов — пометка «текстового слоя нет, OCR недоступен в этой версии» (до v0.2). **`[ОТКЛОНЕНИЕ v03: poppler CLI вместо pdfium, §15-2]`**
- **R-SRC-07.** Правовая аккуратность: скачивание страниц — с уважением к robots/лицензиям (пользовательское действие, предупреждение), архивы хранятся локально; ответственность пользователя фиксируется в документации.
- **R-SRC-08 [РЕШЕНО, Q-07].** OCR (v0.2, опциональный компонент установки): базовый стек — **RapidOCR/PP-OCRv5** (`eslav` rec + mobile det, ~14 МБ моделей, in-process через `ort`/`oar-ocr`; Apache-2.0), **Tesseract 5.5 CLI** (rus+eng, Apache-2.0) — опциональный второй компонент/бенчмарк-фолбэк. Оба за `trait OcrEngine`, поэтому выбор дефолта после спайка B-04 — конфигурация, а не переписывание. Рендер страницы 300 dpi через pdfium, кластеризация строк в колонки; формулы не OCR-ятся. Гейты: CER ≤3% на чистых и ≤8% на деградированных сканах, ≤2 с/стр CPU, компонент ≤40 МБ; при отсутствии компонента — явное предложение установки. OS-native OCR не используется (Apple Vision не поддерживает кириллицу; Windows OCR зависит от языковых пакетов) [S38]. **`[ОТКЛОНЕНИЕ v03: tesseract вместо RapidOCR, §15-3]`**

### 5.7. Документы

#### 5.7.1. Формат `.doc.rde` [РЕШЕНО]

- **R-DOC-01.** Рабочий документ проекта — файл `.doc.rde`: **валидный OOXML-пакет** (WordprocessingML, ECMA-376 Transitional) с дополнительными RDE-частями. Внутри каталога объекта документа: `<name>.doc.rde`, `document.toml` (метаданные объекта, шаблон, привязки), локальные ассеты (если не внутри пакета), `.gitignore` при необходимости.
- **R-DOC-02.** RDE-данные хранятся в **customXml-части** правильно связанным способом (`customXml/item1.xml` + `customXml/itemProps1.xml` + `customXml/_rels/item1.xml.rels` + relationship из корня пакета) — это переживает открытие/сохранение в Word [S10,S11], в отличие от in-body custom XML markup, который Word ≥2010 удаляет [S10].
- **R-DOC-03.** «Надгробие»/детектор потерь — `docProps/custom.xml`: `rdeDocId`, `rdeSchema`, `rdeBodyHash`, список RDE-частей [S10]. При открытии: если `rde:doc` пропала, но надгробие есть → не перезаписывать молча; предложить восстановление (снапшоты/бэкапы/переимпорт) и показать причину.
- **R-DOC-04.** Схема `rde:doc` версионируется (`schema_version`), миграции — упорядоченная цепочка, без «тихих» переписываний; файл с более новой версией открывается read-only с предложением обновить RDE. Контент `rde:doc`: id документа, карта блоков (`block_id ↔ w14:paraId`), вставки/кэши значений, привязки шаблонов и правил, константы/величины, библиография, review-map (id комментария ↔ якорь/автор/дата/статус), карта авторов, хеши содержимого.
- **R-DOC-05.** Сохранение атомарное: временный файл → fsync → rename; ротация бэкапов `.bak` (N последних) + внутренние снапшоты; открытие удерживает advisory-лок (второй экземпляр RDE — read-only или предупреждение).
- **R-DOC-06.** Редактирование в Word Online/OneDrive не поддерживается для проектных документов (customXml там стирается [S10]) — UI предупреждает и предлагает «экспорт копии для Word Online» без RDE-данных.

#### 5.7.2. Режимы и блоки

- **R-DOC-07 [РЕШЕНО].** Режимы просмотра: (1) редактор (основной, WYSIWYG); (2) предпросмотр `.docx` (как будет после экспорта); (3) предпросмотр `.pdf`; (4) просмотр кода документа — блоки/служебные знаки/поля/вставки, полезно для дебага и агента. Режимы могут открываться параллельно во вкладках/сплитах; пометка «страницы/номера в предпросмотре — ориентировочные» (§5.7.9).
- **R-DOC-08.** Каждый абзац/таблица/рисунок/формула — **блок** со стабильным ID; автоматические обновления вставок изолированы по блокам (ошибка одного блока не портит остальные), блоки с ошибками помечаются в дереве документа.
- **R-DOC-09.** В режиме кода показываются: дерево блоков, источник значения вставки (`rde://artifact/...`), состояние кэша, служебные поля; правка кода — только через semantic-операции RDE (не сырой XML), с валидацией.
- **R-DOC-10.** Документ «без шаблона» (free mode) допустим: полный ручной форматинг как в Word; шаблон можно применить/сменить позже с отчётом о переоформлении.

#### 5.7.3. Вставки, обновление документа, поля

- **R-DOC-11.** Виды вставок: значение выхода артефакта (текст/число/CSV-строка/изображение), константа/величина (форматированный текст), рисунок (объект или inline), таблица (из данных артефакта/вручную), **формула (ссылка на project-level объект: `target = rde://formula/<id>@<act_key>`, `render_mode = omml|svg`, документно-локальный номер, ADR-0005)**, подпись рисунка/таблицы, перекрёстная ссылка, запись библиографии и ссылка на неё, дата/поле Word. Вставка имеет ID, URI цели, политику обновления и кэш.
- **R-DOC-12.** «Обновить документ» — транзакция: проверка актуальности целей (act_key/out_hash), пересчёт значений, обновление вставок/номеров/полей, обновление TOC (кэш), запись нового `rde:doc`, бэкап; откат — как у артефактов. Авто-обновление документа — режим (off/manual/auto по аналогии с R-ART-03); при конфликтах показывается отчёт «что изменится» до применения (diff-предпросмотр).
- **R-DOC-13.** Обновление документа никогда не перезаписывает ручные правки молча: ручные изменения в диапазоне вставки фиксируются, конфликт «вставка vs ручная правка» показывается (принять значение / сохранить ручное / отложить).
- **R-DOC-14.** Поля Word: `TOC`, `PAGE`, `NUMPAGES`, `PAGEREF`, `SEQ`, `REF`, `STYLEREF`, `CITATION` (по возможности) — RDE записывает код поля + кэшированный результат; на экспорт выставляется `w:updateFields`; UI честно сообщает: **TOC/номера страниц Word пересчитывает при открытии/печати, `updateFields` не пересчитывает TOC автоматически** [S9]; для финального PDF рекомендуется пересчёт в Word или RDE-предпросмотр. **`[НЕ НАЧАТО]`**
- **R-DOC-15.** Нумерация: сквозная или по разделам/приложениям; настраивается шаблоном/профилем; ручное вмешательство (переопределение номера) фиксируется как override с предупреждением.

#### 5.7.4. Рисунки, таблицы, подписи

- **R-DOC-16.** Рисунок — объект с атрибутами: изображение (из артефакта/файла/вставки), номер (поле/политика нумерации), подпись (rich text: курсив/подстрочные/надстрочные — docx-совместимый rich text-объект), выравнивание, положение (inline/плавающий), keep-with-next подписи.
- **R-DOC-17.** Подпись по правилам выбранного стандарта/профиля (например, «Рисунок 1 — Название» без точки в конце, центр, под рисунком; вариант 7.32/2.105/вуз — параметр шаблона) [S25]. Подпись может содержать вставки (значения артефактов, обозначения величин).
- **R-DOC-18.** Таблицы: ручные и сгенерированные (из CSV/данных артефакта); стили/границы/повтор головки на страницах (`w:tblHeader`), title/подпись над таблицей по правилам; нумерация «Таблица N», «Продолжение таблицы N» — по выбранному правилу [S25].
- **R-DOC-19.** «Сквозное проектирование»: рисунок/таблица/подпись/величина — ссылочные объекты; изменение объекта обновляет все места; обратные ссылки — «где вставлено».
- **R-DOC-20.** Служебные текстовые объекты: docx-совместимый rich text (runs с форматированием, поля, ссылки) — используются подписями, величинами, шапками; видимы пользователю при необходимости, скрыты по умолчанию. Отдельный **тип объекта верхнего уровня** для них не вводится (решение Р2, §5.2), но они доступны в дереве через «служебные объекты».

#### 5.7.5. Формулы

**LaTeX-реестр формул (P0 — проектирование; реализация: P2 — project-level объект формулы, P3 — вставки `omml|svg`, статусы, миграция; P4/P5 — в работе; проект — [ADR-0005](adr/0005-formulas-and-values-as-project-objects.md), реализация — §16; доказательства спайков — [`docs/spikes/formulas-latex.md`](spikes/formulas-latex.md)).** Формула — **project-level служебный объект проекта**: `objects/formulas/<id>/formula.toml` (LaTeX — источник истины; `display`; `numbering {mode: auto|none, label}` — политика и метка, **фактический номер документно-локальный** и назначается при вставке/обновлении документа; `inputs[]` — alias + `mode = hashed|ref` + `source = rde://constants/<id>/<key> | rde://artifact/<id>@<out_hash>/<selector>`; `fragments[]` — URI других формул проекта; кэш-хеши OMML/SVG/PNG, `act_key`, `computed_at`). Одна формула переиспользуется в нескольких документах; документ хранит только вставку `RdeInsert kind="formula"`, `target = rde://formula/<id>@<act_key>`, `render_mode = omml|svg`; актуальность — по `act_key` формулы (входы + фрагменты + LaTeX-источник + версия рендерера, примитивы §7.2); обновление — транзакцией (корни `formula/*` + затронутые `document/<id>`), R-DOC-13 действует (ручная правка не перезаписывается молча). Удаление формулы — проверка «используется в N документах»; вставки без цели — статус «цель отсутствует». SVG-вектор — кэш и режим совместимости (R-DOC-22 п.2): в docx — `asvg:svgBlip` + PNG-fallback (MS-ODRAWXML; LO проверен векторно, Word 2016+ — по спецификации), PDF-гейт «нет растровых формул»; сохранность `svgBlip` в roundtrip обеспечивается фиксом WordCraft-writer в форке (P2.5, ADR-0001 §4, `docs/wordcraft-fork.md`) — без переприменения SVG в RDE. Миграция inline-формул — явной командой.

**Фаза 1 — реализация (2026-10-26, доказательства §16).** Механизм нумерации — **таблица 1×2** (канон §9.4): левая ячейка — display-уравнение по центру, правая — номер `(n)` по правому краю; сквозная перенумерация — `renumber_equations`. Альтернатива WordCraft — автономер через `#` (`m:eqArr` + `resolve_numbers`) — на фазе 1 не используется: OOXML-writer WordCraft пишет сам маркер `#` в `m:t` (`vendor/wordcraft/crates/docx/src/write/math.rs:96`), и номер в Word/LibreOffice выглядит как `E=mc² # (1)` вместо правого поля (проверено LO-рендером PDF); `SEQ Eq` — задел фазы 2 вместе с полями Word (R-DOC-14).

### 5.9. Агент

- **R-AGT-01 [РЕШЕНО].** Встроенный агент — через **ACP (Agent Client Protocol)**: RDE запускает агент-процесс (по умолчанию DSH `--profile acp`; допустим любой ACP-совместимый агент), создаёт сессию с `cwd = корень проекта` и списком MCP-серверов (RDE-сервер + пользовательские), стримит обновления. - **R-AGT-02.** Панель чата: список сессий (проект/глобальные), поток сообщений и tool-call'ов, рендер разрешений (approve/deny), отмена, повтор, fork/restore сессии, выбор модели/провайдера из конфигурации DSH; история сессий хранится в проекте (`.rde/agent/sessions/`, jsonl/sqlite) и не попадает в git по умолчанию (настройкой можно включить).
- **R-AGT-03 [РЕШЕНО].** Cursor-like ссылки: выделение в редакторе/просмотрщике → «В чат» (горячая клавиша/кнопка) → чип-ссылка с URI проекта; поддержка: фрагмент текста, блок/абзац, рисунок/формула/таблица, PDF-страница/регион, выход артефакта, источник, заметка. URI-схема и разрешение — §8.7.2.
- **R-AGT-04 [РЕШЕНО].** PDF-регион (сканы/текстовый слой) — действия: (1) извлечь текст (OCR — v0.2, стек — R-SRC-08; до этого — текстовый слой) → в чат; (2) прикрепить скриншот региона изображением (работает независимо от vision-поддержки модели); (3) сохранить текст в новую заметку; (4) текст в буфер; (5) изображение региона в новую заметку; (6) изображение в буфер. Во всех вариантах, кроме буфера, прикрепляются документ-источник и номер страницы (из v01, сохранено полностью).
- **R-AGT-05 [РЕШЕНО].** Правки агента — **предложения (suggested edits)**: изменения в документах создаются как diff-диапазоны с автором `agent`, кнопками accept/reject (по частям/целиком), предпросмотром; агент не может молча перезаписать пользовательский текст (MCP-инструменты явных «перезаписей» требуют approval/destructive-политики). Ревизии/чекпоинты позволяют откатить работу агента целиком.
- **R-AGT-06 [РЕШЕНО].** Разрешения: дефолт `workspace-write` + policy `ask`; выполнение shell/скриптов — отдельный грант на сессию; destructive-инструменты — approval; `danger-full-access` — только на сессию с явным подтверждением; fail-closed; аудит всех разрешений/действий (файл аудита в `.rde/agent/audit.log`). Маппинг на политики DSH (ask/never + sandbox modes) [S16].
- **R-AGT-07.** Агент может всё, что пользователь, **кроме** управления окнами/раскладкой UI: чтение/правка документов (через предложения), создание/правка объектов, артефактов (включая скрипты), запуск/отмена, источники/заметки/репозитории, обновление документа, экспорт, поиск, git-операции (с approval). Паритет поддерживается матрицей «UI-действие ↔ MCP-инструмент»; расхождения — дефект.
- **R-AGT-08.** Экономия контекста: ограниченный (≈25–30) набор инструментов, диапазонные чтения вместо целых документов, ресурсы для тел, `resource_link` для тяжёлого, инструкции-карта проекта, стабильный порядок инструментов для prompt-cache; при наличии — tools-as-code/PTC режим агента [S36]. Ожидаемый бюджет: ~4–9K токенов на определения (оценка) [S36].
- **R-AGT-09.** Агент и артефакты: агент может написать скрипт/манифест, запустить его (с approval), увидеть лог/provenance; ошибки инструментов возвращаются структурированно (код, причина, подсказка).

### 5.10. MCP-сервер RDE

- **R-MCP-01 [РЕШЕНО].** Реализация на `rmcp` 3.7+ (Rust SDK, официальный), спецификация MCP **2026-07-28** (stateless core: без initialize/sessions, обязательный `server/discover`, `ttlMs`/`cacheScope` в списках, MRTR вместо sampling/elicitation) [S14,S15]. **`[НЕ НАЧАТО: v0.3]`**
- **R-MCP-02.** Транспорты: `stdio` — по умолчанию (для встроенного агента через ACP); `streamable HTTP` — опционально для внешних агентов, только loopback + bearer-токен, выключено по умолчанию (настройка «Разрешить внешним агентам»); аутентификация — токен проекта/сессии, ротация, аудит.

## 7. Модель хешей, DAG и транзакций (нормативная)

### 7.1. Определения

- `H` — SHA-256 (алгоритм фиксируется в `rde.toml`; смена — миграция).
- `output_selector` — относительный путь/glob выхода артефакта.
- `blob_sha256 = H(bytes)` — содержимое файла.
- `tree_hash` — Merkle-корень набора `(relpath, mode, blob_sha256)`, отсортированного по relpath.
- Канонизация JSON — RFC 8785 (JCS); TOML-параметры канонизируются в JSON перед хешированием.

### 7.2. Схема (нормативно)

```
member(g)   = (target_id, output_selector, mode)              # mode ∈ {hashed, ref}
grp_hash(g) = H("rde:grp:1" | g.name | g.mode |
                sorted[ H(target_id, target.out_hash, selector) ])
in_hash(A)  = H("rde:in:1" | sorted[ (g.name, g.mode, grp_hash(g)) ])
script_hash = H("rde:script:1" | runtime_id | entry_relpath |
                H(script_bytes) | sorted[extra_script_files])
params_hash = H("rde:params:1" | canonical_json(A.params))
env_hash    = H("rde:env:1" | runtime_id | platform_triple |
                lockfile_digest | sorted[declared_env_vars_map])
act_key(A)  = H("rde:act:1" | A.type | A.schema_version |
                in_hash | script_hash | params_hash | env_hash)
out_hash(A) = H("rde:tree:1" | sorted[ (relpath, mode, blob_sha256) ])
```

### 7.3. Правила

1. **Только `hashed`-группы входят в `in_hash`.** `ref`-группы записываются в provenance/UI («связано, но не пересчитывается») и не вызывают каскад. Это решает открытые вопросы v01 про независимые входы: групповая семантика явная, для каждой группы задаётся режим; смешанные входы — разные группы.
2. **Устаревание:** `stale(A) ⇔ act_key ≠ recorded_act_key ∨ отсутствуют блобы выходов ∨ out_hash ≠ recorded_out_hash`. Причины для UI: «изменились входы», «изменился скрипт», «изменились параметры», «изменилось окружение», «потеряны/повреждены выходы», «ручная правка выходов».
3. **Циклы:** только по `hashed`-рёбрам; обнаруживаются при сохранении манифеста (DFS-раскраска) и при загрузке проекта; проект с циклом — ошибка с цепочкой.
4. **Порядок обновления:** топологическая сортировка по `hashed`-рёбрам; `ref`-рёбра исключены из порядка (могут быть визуальными циклами).
5. **Целостность:** ручная правка выхода изменяет `out_hash` → `integrity_warning`; действия: пересчитать (перезаписать), принять как новое состояние (зафиксировать как «мутация вне RDE» с автором), восстановить из CAS.
6. **Детерминизм:** `env_hash` фиксирует окружение; уровень воспроизводимости «та же машина» в v1 отображается в UI; полный контейнерный/nix-уровень — `[ОПЦИЯ]`.
7. **Транзакция обновления:** 
   `prepare(новая версия набора акт-ключей/корней) → write journal "prepared" → выполнение → import outputs в CAS → verify out_hash → journal "committed" (атомарно) → switch current roots`.
   Перед выполнением — снапшот текущих корней; откат = переключение current на предыдущие корни (O(1)), старые блобы сохраняются окном отката.
8. **GC:** mark-and-sweep от корней: current roots + окно отката (N/время) + pin'ы (экспорты/шаринги) + снапшоты документов; перед удалением — отчёт; pin'ы не удаляются.
9. **Provenance:** `runs/<run_id>/provenance.json` (SLSA-подобно [S27]): `subject` (out_hash), `externalParameters` (артефакт, act_key, params, инициатор), `resolvedDependencies` (hashed-входы с URI `rde://artifact/<id>@<out_hash>`), `runDetails` (+ RDE: git_commit, git_dirty, env_lock_digest, platform, script_hash, exit_code, log_digest, время).
10. **Совместимость с git:** манифест хранит `out_hash` (идентичность выходов) — git диффит происхождение без коммита бинарных выходов (модель DVC без sidecar-файлов) [S29,S30].

## 8. Архитектура решения

### 8.1. Базирование на WordCraft и стратегия субмодуля [РЕШЕНО]

**Проверенные факты о WordCraft** (v0.10.0, коммит `9130181a`, релиз 2026-10-22) [S1,S2,S6]:
- Rust/edition 2024, rust-version 1.95; 16 crates L0–L6 (geom → doc/fonts/proof → layout/docx/docbin/formats → render/pdf → engine → mcp → ui-egui → apps); ~800 тестов, `cargo xtask ci` (формат, clippy, слои, wasm).
- egui 0.36/eframe 0.36; нативное GPU-приложение (не Electron/Tauri), web-сборка через Trunk/wasm (eframe), с ограничениями (нет control-канала, нет OPFS, сохранение через File System Access/download).
- **642 команды** (`CommandSpec{id,label,location,shortcut,params,mutates,enabled,run}`) — управления ribbоn/CLI/control-каналом/MCP; `Session::run(id, Value)`, публичные `doc`, `sel`, `view`, `undo`, `macros`, `prefs`; `Registry` с описаниями [S2].
- **MCP** (stdio, 16 tools: list_commands/execute/batch/new_document/open/save/type_text/select_text/get_text/inspect_document/render_page/parity/screenshot/click/key/ui_inspect) + два корневых ресурса; два бэкенда — Headless и Remote (`--connect`, control-протокол JSON-lines на localhost, 256-битный ключ) [S3,S4].
- **OOXML**: docx read/write Transitional, Strict — read-only; `.doc` только чтение; PDF только запись (≈80%); части, которые WordCraft не моделирует, сохраняются `Document.passthrough`/`UNMODELLED_ROOTS`/`CUSTOM_XML_ROOTS` (opaque bytes); **создавать/править произвольные parts командами нельзя** — внешняя пост-обработка пакета обязательна [S2,S5].
- Комментарии/трек-ченджес — читаются/пишутся; поля TOC/SEQ/REF и т.п. — генераторные команды; формулы OMML; charts/SmartArt — read-only; mathType-OLE — только картинка; макросы — JSON-последовательности команд (не код); плагинов нет; проекта/файл-вотчера/мультидокумента нет; PDF-просмотра нет; VCS нет [S5].
- Стратегические риски: проект создан 2026-10-07, 15.8k★, 199 контрибьюторов, 928 открытых issues/790 PR, 390 коммитов за 4 дня; **альфа**, docx на реальных файлах не тестировался (gap #1), пагинация расходится с Word (gap #4), charts read-only (gap #13) [S1,S5].

**Стратегия [РЕШЕНО].**
1. Репозиторий RDE — отдельный монорепозиторий. `vendor/wordcraft` — **git-submodule**, зафиксированный на теге `v0.10.0` (коммит `9130181a`); `vendor/craft-libs` — субмодуль с пином на ревизию `9f75d3ca…`, необходимую WordCraft; `[patch.crates-io]` для `krilla` повторяется в корне RDE (см. `Cargo.toml` WordCraft [S6]).
2. **RDE-код — снаружи субмодуля**, в собственных crates (`rde-*`), зависит от публичных crates WordCraft по path. RDE не «смешивает» код в WordCraft.
3. **Патч-серия** — минимальный набор патчей в `patches/wordcraft/`, применяемый `xtask` после checkout субмодуля; каждый патч — кандидат в upstream PR; цель — держать ≤3 патчей, feature-gated, с CI-проверкой «патч применяется чисто».
4. Основной патч — экспорт **панели-виджета документа** (рендер/ввод rich-редактора) для встраивания в док RDE (решение Р3). Всё остальное — внешними слоями: команды, MCP, пост-обработка zip, ACP, UI-панели RDE.
5. Синхронизация с upstream — по релизам (1–3 мес.), вручную: bump пина + ребейз патч-серии + прогон регрессии; «живой merge» main не практикуется.
6. Дистрибутив RDE собирается с включёнными в поставку исходниками (MIT/Apache), NOTICE/атрибуция WordCraft; бренд WordCraft/ArtCraft в UI RDE не используется [S7].

### 8.4. Хранилище, индекс, транзакции

- **CAS** — блобы `sha256` под `cas/sha256/…`, zstd для крупных/сжимаемых, дедупликация; immutable.
- **Деревья** — `trees/<tree_hash>.json`: `[(relpath, mode, blob)]`, служат «деревом версии».
- **Журнал** — `updates/<txid>.json` (схема §7.3 п.7), fsync перед публикацией; атомарная смена `current` через запись `current.toml`/rename.
- **Индекс** — SQLite (`rusqlite`): объекты, рёбра графа, статусы, FTS по текстам, история запусков, агент-сессии; всегда пересоздаваем из файлов/CAS (source of truth — файлы).
- **Trash** — удаление объектов в `.rde/trash/<ts>/…` с восстановлением; ретенция.
- **Совместимость**: манифесты — TOML как hand-editable; JSON Schema генерируется `schemars`, валидируется `jsonschema` на load и save; правка — `toml_edit` (сохранение комментариев/порядка) [S30].

### 8.5. Формат `.doc.rde` (пакет)

```
<name>.doc.rde (zip)
├─ [Content_Types].xml
├─ _rels/.rels
├─ docProps/core.xml, docProps/app.xml
├─ docProps/custom.xml            # tombstone: rdeDocId, rdeSchema, rdeBodyHash, rdeParts
├─ word/document.xml, styles.xml, numbering.xml, settings.xml, …  # WordCraft-модель
├─ word/comments.xml, commentsExtended.xml, commentsIds.xml, people.xml  # пометки/авторы
├─ customXml/item1.xml            # rde:doc (единый RDE-документ)
├─ customXml/itemProps1.xml
├─ customXml/_rels/item1.xml.rels # связи на дочерние части (если появятся)
└─ docProps/thumbnail.jpeg (опц.)
```

- Wiring: relationship из `_rels/.rels` на `customXml/item1.xml`, `itemProps1` обязателен — без него Word теряет item [S11].
- `rde:doc` (XML, namespace RDE, `schema_version`): карта блоков, вставки/кэши, поля/политики нумерации, шаблон/правила, константы/величины, библиография, review-map, авторы (карта ULID→данные), хеши; вложенные ассеты — только через `item1.xml.rels` (не «сироты») — сиротские части теряются [S10,S11].
- Анкоры: `w14:paraId` (сохраняются Word/LO), скрытые bookmarks `_RDE_*` (≤40 символов, без пробелов), content controls с `w:tag="rde:<kind>:<ulid>"` — как резервные анкоры [S10–S14].
- Вставки в теле: content controls (`sdt`) с `w:tag="rde:<kind>:<ulid>"` и кэшированным rich-text `w:sdtContent` — **механизм по умолчанию (mechanism of record)**; RDE обновляет кэш и при загрузке пересинхронизирует store из `sdtContent` (последнее намерение пользователя не теряется).
- `dataBinding` к `rde:doc` — **опциональный режим «Word-live»** (по умолчанию выключен) и только для простых скалярных значений (plain text/date): при наличии `w:dataBinding` Word принудительно делает контрол plain text (MS-OE376 §2.1.193), а co-authoring/Word Online ломают binding [S37]. Для подписей, номеров и величин с форматированием binding не используется. Wiring self-heal: RDE проверяет `itemID ↔ storeItemID ↔ rels ↔ content types` при каждом открытии и восстанавливает недостающие звенья; проверка — спайк B-03 (§13).
- Схема/миграции — §5.7.1; экспорт/импорт — §5.7.9.

### 8.6. UI-архитектура

- **egui 0.36** (как в WordCraft) + `egui_dock` 0.21.x (`^0.36`); `egui_extras` (таблица/дерево), `egui_tiles` — запасной вариант, если понадобится (пин egui ^0.37 несовместим без апгрейда WordCraft) [S18].
- Панели: дерево (virtualized), центральный DocArea (вкладки: документ/предпросмотр docx/pdf/код/сравнение/источник/заметка), правая AgentPanel, нижняя LogsPanel/StatusPanel, левая нижняя «Задачи/Уведомления».
- **Документ** — embedding через минимальный патч WordCraft: экспорт `DocView`-виджета (canvas+ввод+минимальные хуки) и `Services`-инъекция; полный ribbon WordCraft не обязателен — RDE даёт свою панель инструментов/меню (паритет форматирования через существующие команды).
- **Webview — только точечно**: egui+wry (child webview) не композитится с egui-оверлеями и на Linux ограничен X11 [S19]; поэтому агент — нативная панель (ACP), PDF — native pdfium, Monaco/CodeMirror не используются в v1 (просмотр кода — egui-виджет с tree-sitter-подсветкой, `[ОПЦИЯ]` позже).
- **PDF** — `pdfium-render` (BSD-3 через pdfium; MuPDF отклонён — AGPL) [S20,S22]: рендер страницы, текстовый слой/char-boxes, поиск, выделение региона, DPI/масштаб, кэш страниц.
- **Запуски/логи** — не полноценный терминал: ANSI-совместимый просмотр логов (`alacritty_terminal`/свой SGR-парсер — `[ОПЦИЯ]`); PTY (`portable-pty`) — только если нужен интерактивный сценарий (фаза 2).
- **Код документа**: дерево блоков/вставок/полей, служебные знаки; не сырой XML; прыжок «источник данных» → объект/артефакт.
- **Темы/иконки/меню/диалоги**: `muda`, `rfd`, `arboard` [S18]; все тяжёлые операции — фоновые потоки с каналами прогресса; UI-тесты — `egui_kittest`.

### 8.7. Агентная подсистема

#### 8.7.1. ACP-интеграция [РЕШЕНО]

- RDE запускает агент как дочерний процесс: `dsh --profile acp` (DSH MIT, локальный пакет 0.2.0-rc.2; ACP v1: session/new/list/resume/close, set_config_option, cancel, per-session MCP-серверы, permissions) [S16,S17].
- `session/new`: `cwd` = корень проекта; `mcpServers` = [{ name: "rde", transport: stdio, command: RDE-бинарь `mcp serve` }] (+ пользовательские MCP); политики DSH: `sandbox=workspace-write`, `approval=ask` по умолчанию.
- RDE рендерит `session/update` (сообщения, tool calls, permission requests) в нативной панели; кнопки approve/deny; отмена; fork/resume сессий; конфигурация провайдеров/моделей — из DSH-профиля, редактируется в настройках RDE (проксирование конфигурации, без дублирования API-ключей в RDE).
- Альтернативный агент: любой ACP-совместимый; если DSH не установлен — RDE предлагает установку компонента (инсталлятор) и/или подключение внешнего ACP-агента.
- **Отклонено**: iframe web-UI DSH (DSH отклоняет cross-site: Origin/Host + `SameSite=Strict` cookie, `sec-fetch-site: cross-site` → 403), встраивание чужого SPA в webview (нестабильно, композитинг) [S16,S19]. **Отклонено**: SDK-профиль DSH как основной (нет cancel/close в sdk-профиле).

#### 8.7.2. Контекст-ссылки (Cursor-like) [РЕШЕНО]

URI-схема (стабильные ID, revision-scoped):

```
rde://project/<project_id>
rde://doc/<doc_id>@<rev>#block/<block_id>
rde://doc/<doc_id>@<rev>#para/<w14:paraId>
rde://doc/<doc_id>@<rev>#comment/<comment_ulid>
rde://source/<source_id>/<content_hash>?page=<n>&bbox=<x0,y0,x1,y1>&pageSize=<w,h>
rde://artifact/<artifact_id>@<out_hash>/<relpath>
rde://note/<note_id>
rde://template/<pack_id>@<version>
```

Разрешение ссылки: текст диапазона + метаданные (документ/страница/bbox) + опциональный raster-кроп (PNG, image-block) + ленивая подгрузка тела (ресурс/инструмент). В чат вставляется чип; тело передаётся агенту только когда нужно (`resource_link` + диапазонные чтения). Выделение в PDF: текст (из текстового слоя) и/или изображение региона; пишется источник + страница. При редактировании документа link revision-scoped; при устаревании — re-anchor (paraId → quote-selector), помечать «ссылка обновлена».

#### 8.7.3. Правки, checkpoints, разрешения

- Предложения: MCP-инструменты `doc_suggest_edit`/`doc_insert` создают changeset (диапазон + автор agent + исходный текст), UI показывает diff; accept/reject по частям; результат пишется как правка с автором-агентом; «принять всё» — явное действие.
- Checkpoints: перед каждой модель-записью/опасным инструментом RDE фиксирует ревизию (документ/объекты); «откатить работу агента» = восстановление ревизии/снапшота.
- Approval: destructive-инструменты (удаление/перезапись/commit/run) — UI-approval с диффом; shell/скрипты — отдельный грант; аудит.
- Границы: агент не управляет окнами/раскладкой; не имеет доступа к секретам; сеть — по политике провайдера.

Аннотации: чтения — `readOnlyHint: true`; записи — `destructiveHint` где применимо; все параметры — стабильные ID (ULID/hash), не сырые тела; пагинация/диапазоны/лимиты; ошибки — коды `RDE_*` + человекочитаемая причина; список инструментов детерминирован (prompt-cache). ### 8.8. Сервер и коллаборация (фаза 3, архитектурный эскиз)

- `rde-server` (axum, Rust): self-hosted, single-tenant/небольшие команды; API: публикация документа/пакета, share-ссылки с токенами (истечение/отзыв), web-viewer (PDF-рендер или wasm-рендер + оверлей аннотаций), аннотации (W3C Annotation Data Model JSON как формат обмена [S13]), синхронизация пометок обратно в проект, аккаунты — **[РЕШЕНО, Q-11]:** приглашения + локальные аккаунты, доступ по токен-ссылкам с истечением/отзывом, TLS обязателен на reverse-proxy, OAuth/OIDC — опция позже; аудит.
- Статусы ревью: open/resolved/rejected; ответы/threads; уведомления (email — опция); экспорт/импорт W3C JSON-LD.
- Real-time co-editing (CRDT, Yjs/Automerge/Loro) — отдельная фаза после сервера; документная модель (блоки с ID) к этому готова; в v02 не проектируется детально.
- Безопасность сервера: TLS обязателен (reverse-proxy), rate-limit, токены в URL не логируются, per-doc ACL, отзываемые ссылки, offline-режим проекта не ломается.

### 8.9. Расширяемость

- **Командный реестр** — единый способ действий: команды RDE (проект/объекты/документ/агент) + команды WordCraft (через `Registry`/`Session::run`) доступны из меню/палитры/горячих клавиш/MCP (маппинг). Новые действия добавляются как команды — консистентность UI/агента.
- **MCP как публичный API** — основной интеграционный контур v1; сторонние инструменты/агенты подключаются без плагинов.
- **Шаблоны/стандарты** — пакеты данных (TOML+ресурсы), устанавливаются/обновляются отдельно; пользовательские профили; шаблоны могут иметь ограниченные хуки (декларативные выражения; WASM-хуки — `[ОПЦИЯ]`), но не произвольный код в глобальном шаблоне.
- **Плагины [РЕШЕНО, Q-12].** Публичный API — **WASM-плагины** (wasmtime/WASI): песочница, кросс-языковая поставка, permissions-манифест и подпись; публичный API и реестр — после v1.0, архитектурный задел (командный реестр, trait-границы доменов, манифест плагина) — в v1. Rust-native плагины как публичный ABI не поддерживаются (нестабильный ABI, нет песочницы); внутренние расширения — обычные `rde-*` crates.
- **Формат данных** — JSON Schema публикуется; сторонние генераторы артефактов/шаблонов могут писать манифесты; `rde-cli` — headless-точка интеграции.

### 8.10. Сборка, дистрибуция, CI

- **Сборка**: Rust 1.95+ (пин toolchain в `rust-toolchain.toml`), edition 2024; `xtask`: bootstrap субмодулей + patch-серия + build/test/lint/fmt; `cargo deny` (лицензии/уязвимости); wasm-сборка WordCraft не входит в v1-артефакты.
- **Инсталляторы**: Windows MSI (per-user, компоненты), macOS DMG (notarized/signed), Linux AppImage/Flatpak/deb/rpm (по образцу WordCraft [S1]); portable-режим; компоненты (R-SET-02); удаление обратимо (в т.ч. PATH-интеграция на Windows).
- **Обновления**: единый minisign-подписанный `manifest.json` (версии артефактов по платформам, SHA-256, `min_supported_version`, канал, rollout %, массив `components[]` для PDF/OCR/Python/Node/R/DSH); порядок проверки: TLS → подпись манифеста → SHA-256 артефакта → платформенная подпись → anti-rollback → установка → health-check → авто-откат на N-1; каналы stable/beta — отдельные подписи; платформенные механизмы и риски — §8.11 [S39].
- **CI**: Linux — unit/integration/UI-kittest/hash-property; Windows — сборка + docx round-trip + Word COM nightly (лицензионный Office на self-hosted раннере); macOS — сборка/подпись; Linux — Flatpak/AppImage smoke; артефакты fidelity-отчёта публикуются.
- **Релизный чек-лист**: patch-серия применяется чисто; лицензии; NOTICE; миграции схем; бенчмарки; фикстуры ГОСТ; обновление документации.

### 8.11. Механизмы обновления и установки (решено Q-03) [S39]

- **Один владелец установки на платформу** (иначе MSI-база и self-update расходятся): Windows — MSI-владелец (приложение скачивает следующий MSI и запускает его; portable-режим — `self-replace`/`self_update` для exe); macOS — подписанный/нотаризованный `.pkg`/`.app`, замена бандла helper'ом с повторной проверкой `codesign -v` и re-staple; Linux — AppImage (+zsync/`zstd --patch-from` дельта, полный пакет всегда тоже публикуется) либо deb/rpm; **Flatpak** — собственный updater отключён (обновление через remote); portable — `self-replace`.
- **Компоненты** (OCR-модели, uv/python, Node, R, DSH-рантайм) — всегда app-managed: per-user в каталог данных, версии/файлы/env-изменения фиксируются в локальном `installed.json`; **никаких записей в глобальный PATH** — один shim-каталог (удаляется при деинсталляции), инструменты резолвятся по абсолютным путям из манифеста; Windows env — `HKCU\Environment` + `WM_SETTINGCHANGE`, с сохранением исходных значений для обратимого удаления.
- **Безопасность обновлений:** подпись манифеста (minisign), anti-rollback (`min_supported_version` + монотонный счётчик), staged rollout в манифесте, `cargo-auditable`/`cargo-audit`/`cargo-deny` в CI, подписанные релизы (Authenticode/Azure Artifact Signing — Windows; Developer ID + notarization — macOS; Linux — подпись манифеста/AppImage).
- **Дельта-обновления** — опция после замера (ожидание 5–20 МБ патча для 100–200 МБ приложения — `[НЕ ПРОВЕРЕНО]`, нужен реальный замер); полный пакет всегда доступен как fallback.
- **Инструменты (2026):** `minisign`/`minisign-verify`, `self-replace`, `cargo-packager-updater` (формат Tauri-фида без Tauri) — кандидаты; `cargo-wix` (MSI), `cargo-dist`/`axoupdater`, Velopack — рассмотрены; выбран **собственный updater на подписанном манифесте** (максимальный контроль над компонентами, каналами и anti-rollback).

## 11. Критерии приёмки

### 11.1. Продуктовые (сценарии)

1. **С1–С6 из §3.3 проходят end-to-end на релизных сборках** Windows/macOS/Linux с эталонными проектами; для каждого — записанный автотест/ручной чек-лист (Приложение E).
2. **Экспорт в Word:** документ по 7.32, собранный в RDE, открывается в Word 2016/2019/2021/365 без диалогов восстановления; комментарии/трек-ченджес/поля присутствуют; отчёт RDE «потерь данных не обнаружено».
3. **Ревью-цикл:** руководитель (внешний Word) оставляет ≥10 комментариев и правок → импорт: ≥95% комментариев сопоставлены автоматически, остальные в очереди сирот; правки тела доступны как suggested edits.
4. **Агент:** 10 типовых задач (чтение/правка/генерация артефакта/поиск/экспорт) выполняются через MCP; все действия аудированы; любое изменение откатывается.
5. **Восстановление:** kill -9 в момент сохранения/обновления/экспорта не приводит к потере зафиксированных данных; диагностика сообщает о незавершённой транзакции.

### 11.2. Технические (метрики)

| Метрика | Порог |
|---|---|
| WordCraft/docx round-trip: части пакета сохранены | 100% (для RDE-документов), отчёт при отклонениях |

### 14.2. Отклонённые альтернативы (и почему)

| Альтернатива | Почему отклонена |
|---|---|
| Web-first / Tauri-оболочка | Документный редактор и файлы/скрипты/git — нативные; JS-переписывание редактора уничтожило бы переиспользование WordCraft; webview-композитинг проблематичен [S18,S19] |
| Отдельный workspace на git-зависимостях WordCraft | Нет crates.io/стабильного API, git-депы + патчи krilla/craft-libs → нестабильная сборка [S6] |
| RDE без форка, WordCraft как внешний редактор по MCP | Нет единого проекта/UI, нарушает концепцию «IDE для отчёта» |
| Все объекты — zip-контейнеры `.xxx.rde` (v01) | Плохо для git/внешних инструментов/агентов; проблема «всё запаковано» из v01; выбран каталог-first + `.doc.rde` только для документов |
| Один встроенный язык скриптов (Lua/Rhai/JS/WASM) | Не даёт научную экосистему (numpy/matplotlib/R); subprocess-модель проще и мощнее [S32] |

| SingleFile для веб-архива | AGPL-3.0 [S24]; monolith CC0-1.0 [S23] |
| iframe/webview с web-UI DSH | DSH отклоняет cross-origin (Origin/Host, SameSite=Strict, sec-fetch-site), композитинг egui+webview нестабилен [S16,S19]; выбран ACP |
| Гарантия «пагинация 1:1 с Word» | Word не хранит пагинацию; PAGE/TOC/TOC-номера — кэш полей; updateFields не пересчитывает TOC [S8,S9] |
| Word Online для проектных документов | customXml стирается Office Online [S10] |
| Real-time CRDT и сервер в v1 | Дорого/рискованно; сценарий v1 закрывается docx-комментариями (решение 1.9) |
| Требовать MathType-экспорт | Проприетарный SDK/приложение; OMML закрывает 95% сценариев [S5] |
| Полный CSL/citeproc с ГОСТ | Только numeric-стиль ГОСТ (CC BY-SA), author-date нет [S26]; свой форматтер проще и юридически чище |
| Подробные оценки трудозатрат в ТЗ | Решение владельца (3.8): оценки быстро устаревают |
| Tesseract как единственный/основной OCR | Слабее на деградированных сканах (CER 12.9% в исследовании по кириллице), сложная упаковка C++-либы на 3 ОС [S38]; выбран RapidOCR-дефолт + Tesseract-фолбэк |
| Drag-tear-off вкладок в v1 | Нет библиотечной поддержки, Wayland не даёт позиций/глобального курсора; v1 — команды переноса, drag — спайк [S40] |
| Глобальная запись в PATH при установке компонентов | Ломает окружение пользователя и необратима; выбран app-scoped резолвинг + один shim-каталог [S39] |
| OAuth/OIDC как обязательная аутентификация сервера в фазе 3 | Лишняя сложность для self-hosted; приглашения+аккаунты закрывают сценарий, OAuth — опция |
| Rust-native plugin ABI | Нестабильный ABI без песочницы; выбран WASM-плагины [S39] |
| Плагины/маркетплейс в v1 | Отложено; MCP — публичный API v1 |

## Приложение D. Детализация ключевых потоков (shine-detilize)

### D.1. Создание проекта и первого артефакта

1. Пользователь: «Новый проект» → мастер: имя, каталог, шаблон (7.32/лабораторная/free), авторы (по умолчанию из настроек), дефолтный rebuild-режим.
2. RDE: создаёт каталог, `rde.toml`, `rde.lock`, `.gitignore`, `objects/`, `exports/`, `.rde/`, `git init` (если нет), первый коммит «project init» (автор — выбранный). Ошибки: каталог не пуст → предупреждение и выбор «как есть/в подкаталог»; нет прав/ФС → понятная ошибка, ничего не создаётся частично (транзакция создания).
3. Пользователь: «Новый артефакт» → тип `compute`, runtime `python`, окружение проекта → RDE создаёт папку, `artifact.toml`, `script.py`-заглушку, `.gitignore` (`out/`, `__pycache__/`), добавляет в индекс; валидация манифеста (JSON Schema) с подсветкой ошибок.
4. Пользователь: «Добавить вход» → выбирает файл `inputs/experiment.yaml` (копируется/регистрируется хеш) или выход другого артефакта (создаёт `hashed`-группу). Ошибки: вход не существует/недоступен → предупреждение, сохранение блокируется до исправления (или сохраняется «черновик» с явным статусом).
5. «Обновить» → `rde-run`: подготовка среды (первый раз: `uv sync` с прогрессом/согласием), запуск `script.py`, стрим логов в панель, импорт выходов в CAS, запись `run` + provenance, переключение текущих корней (транзакция). Ошибки: скрипт упал → статус `failed`, лог/exit code/provenance, прежние выходы остаются текущими (не перезаписаны); timeout/cancel — процесс-группа убита, статус `failed/cancelled`, частичные файлы не импортируются.
6. «Обновить связанные» → `rde-dag` строит топоплан только из `outdated`; каждое действие — отдельный run в рамках одной транзакции «пачки»; ошибка одного downstream останавливает пачку (настройка: продолжать по независимым ветвям) и предлагает откат всей пачки.
7. «Откатить обновление» → переключение на корни до пачки; документы/артефакты, ссылавшиеся на результаты, показывают «обновлены с откатом» (уведомление); блобы не удаляются (в окне).

### D.2. Вставка рисунка из артефакта и экспорт

1. В дереве/панели артефакта пользователь выбирает `out/plot.svg` → «Вставить в документ»; RDE создаёт служебный объект «рисунок» с привязкой `rde://artifact/<id>@<out_hash>/out/plot.svg` и политикой «обновлять при обновлении документа».
2. В документе появляется блок-рисунок + подпись: номер = SEQ/нумерация по правилу шаблона, текст подписи — rich-text c вставками (например, обозначение величины из объекта-константы). В `rde:doc` фиксируются блоки, вставки, кэш.
3. При изменении артефакта → его `out_hash` меняется → документ показывает «устаревшие вставки (1)». «Обновить документ»: проверка целей, обновление рисунка (реимпорт изображения в пакет WordCraft-командой/пакетным слоем), обновление подписей/номеров, кэш TOC; транзакция + бэкап; diff-предпросмотр до применения.
4. Экспорт `.docx`: RDE собирает «чистый» пакет (без RDE-частей), прогоняет гейты (§R-DOC-38), пишет `exports/<name>.docx`, отчёт fidelity. Ошибки валидации → экспорт блокируется с указанием элементов (режим «всё равно экспортировать» — только с предупреждением и логом).

### D.3. Ревью-цикл

1. «Экспорт на ревью»: `.docx` (комментарии + review-map + комментарии существующих пометок) в `exports/`, плюс запись в истории ревью (кто/когда/что отправил).
2. Руководитель открывает в Word, комментирует/правит, возвращает файл (почта/диск). Пользователь кидает файл в RDE (drag&drop) → «Импорт ревью».
3. RDE: сохраняет неизменяемый снапшот возврата; парсит comments*/people/ревизии; сопоставляет пометки; создаёт/обновляет review-объекты; правки тела — suggested edits; формирует отчёт: сопоставлено/сироты/повреждённые части/потерянный customXml.
4. Пользователь разбирает: принимает/отклоняет правки, привязывает сирот (клик на место), отвечает на комментарии, помечает resolved. RDE обновляет `.doc.rde`, review-map, при необходимости — git-коммит.
5. Повторный цикл: следующий экспорт содержит уже resolved-статусы и новые комментарии; сравнение с прошлым ревью.

### D.4. Агент: от ссылки до принятой правки

1. Пользователь выделяет абзац в редакторе → `Ctrl+Alt+A` «В чат» → в поле чата чип `rde://doc/<id>@<rev>#block/<id>` (+ текстовая выжимка).
2. Панель агента отправляет ACP `session/prompt` с content blocks (resource_link + текст + инструкции); RDE MCP-сервер доступен агенту (stdio) — агент читает контекст диапазоном, при необходимости запрашивает окружение.
3. Агент вызывает `doc_suggest_edit` → RDE создаёт changeset, атомарно обновляет черновик документа и показывает его в diff-панели с подписью «агент».
4. Пользователь: «Принять» (частично/полностью) или «Отклонить» / «Откатить» (checkpoint). Принятые правки фиксируются с автором-агентом; изменения видны в истории документа и в git (по действию пользователя).
5. Если агенту нужен запуск артефакта — approval-диалог с командой/диффом манифеста; после запуска provenance фиксирует инициатора-агента; лог доступен пользователю.

### D.5. Сбои и краевые случаи (edge cases)

| Ситуация | Поведение RDE |
|---|---|
| Цикл в hashed-графе | Сохранение манифеста отклоняется; показать цепочку цикла |
| Вход указывает на несуществующий артефакт/выход | Статус `blocked` + причина; обновление невозможно; предложить починить/удалить ссылку |
| Блоб выхода отсутствует в CAS (очистка/повреждение) | `integrity_warning`/`stale`; «восстановить из снапшота/пересчитать» |
| Скрипт пишет вне объявленных `outputs` | Ошибка запуска после завершения; посторонние файлы не импортируются, лог; манифест можно поправить и перезапустить |
| Timeout/отмена во время записи файлов | Процесс-группа убит; работа в temp-каталоге; частичные файлы отброшены; текущие корни не изменены |
| Параллельные обновления одного артефакта | Очередь/лок; второй запрос ждёт или отклоняется с понятным статусом |
| Ручная правка выхода | Детект по `out_hash`; выбор: пересчитать/принять как мутацию/восстановить |
| Внешний Word изменил `.doc.rde` | Очередь «Внешние изменения»; merge-отчёт по R-DOC-36; при `strict` — блокировка до решения |
| Word потерял customXml (Online/сторонний редактор) | Tombstone-детект при открытии; запрет молчаливой перезаписи; мастер восстановления (снапшоты/бэкапы/переимпорт) |
| Файл проекта новее схемы | Read-only режим + сообщение об обновлении RDE; данные не изменяются |
| Перемещение/клонирование каталога проекта | Относительные пути; индекс пересоздаётся; абсолютные внешние пути — с предупреждением и перепривязкой |
| Очень большой проект (10k+ объектов) | Виртуализация, ленивая загрузка, инкрементальный индекс; операции с прогрессом |
| Диск переполнен | Предварительная проверка места, отказ от транзакции до фиксации, понятная ошибка; текущее состояние не повреждено |
| Крак во время миграции схемы | Бэкап перед миграцией; повторный запуск идемпотентен; при неудаче — восстановление бэкапа |
| Сеть недоступна (источник/агент/обновление) | Офлайн-режим: архив источника используется, агент — ошибка провайдера с retry, обновления отложены |
| Секреты в логах/агентском контексте | Санитизация env-переменных, запрет логирования секретов, предупреждение пользователю |

## 15. Реестр отклонений реализации от ТЗ v02 (нормативно)

Отклонение = код реализует иначе, чем требует v02. Каждое либо принято этим документом, либо подлежит возврату к ТЗ. Молчаливых отклонений быть не должно.

### 15-1. Докинг: кастомные панели вместо `egui_dock` — ПРИНЯТО v03
- **Требует v02:** R-UI-02 [РЕШЕНО], §8.6 — вкладки/сплиты/докинг через `egui_dock ^0.36`.
- **Сделано:** собственные панели (`egui::Panel`), 5 вкладок центра + лента; `egui_dock` не подключён.
- **Доказательство:** `rde/Cargo.toml` (нет зависимости), `crates/rde-ui/src/lib.rs` (Panel::left/right/top/bottom).
- **Обоснование принятия:** DocView WordCraft — единый canvas, которому нужен стабильный центральный регион; `egui_dock` дублирует управление панелями и конфликтует с ribbon-лентой (v03 §10.1 UI). Докинг как продуктовое требование сохраняется, но реализуется собственным слоем раскладки.
- **Решение:** принять; §8.6 скорректирован: «докинг в одном окне собственным слоем; `egui_dock` — допустимая замена при пересмотре».

### 15-2. PDF: poppler CLI вместо pdfium — ВОЗВРАТ к ТЗ в v0.2
- **Требует v02:** R-SRC-06, R-DOC-37, §8.6 — pdfium (BSD-3, `pdfium-render`).
- **Сделано:** внешние CLI `pdftotext`/`pdfinfo`/`pdftoppm` (Linux-only), `rde-sources/src/lib.rs:9-12,406-430`.

### 15-3. OCR: tesseract вместо RapidOCR — ВОЗВРАТ к ТЗ в v0.2

### 15-5. Шрифты: DejaVu вместо Liberation OFL — ТРЕБУЕТ РЕШЕНИЯ ВЛАДЕЛЬЦА

## 20. Правила ведения ТЗ

1. **Канон:** `rde/docs/tz-03.md` (версионируется в git, публикуется). Рабочая копия — `.agent/tz-03.md`; при расхождении прав канон в репозитории.
2. **Изменение:** любой коммит, меняющий требование/решение, обновляет этот файл: версия не меняется, но в §0.1 добавляется строка и в `CHANGELOG.md` — запись.
3. **Новая версия (v04):** только при смене ключевых решений (формат документа, архитектура, лицензии, фазы) — с полным ре-солвом, как v01→v02.
4. **Статус-маркер:** ставится только с доказательством (§0.3). Регрессия — сначала фикс, потом маркер.
5. **Аудит:** перед каждой вехой — сверка «ТЗ ↔ код ↔ docs»; результат — обновление §16/§17, не отдельный документ.
6. **Никаких оценок трудозатрат** (решение владельца действует).
7. **Отклонение без записи в §15** считается дефектом и блокирует веху.
