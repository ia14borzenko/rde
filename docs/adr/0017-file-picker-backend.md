# ADR-0017 — Системный выбор файла/папки в GUI («Проводник…»)

- **Статус:** принято (2026-10-29, итерация `gui-pickers`)
- **Контекст:** GUI-02 / R-UI-08 (аудит: «весь функционал из интерфейса»)
- **Связанные документы:** [docs/gui-coverage.md](../gui-coverage.md), ADR-0001 §3 (внешние CLI вместо
  системных библиотек), ADR-0003 (отклонения от ТЗ).

## Контекст

До итерации все пути в GUI RDE вводились только текстом: «Открыть проект», «Импорт .docx»,
«Новый проект», «Программа ACP-агента». Пользователь должен был помнить путь и набирать его
руками — опечатка обнаруживалась только после действия (или не обнаруживалась вовсе).

Требования к решению:

1. **Системное окно** выбора файла/каталога (как в ОС), а не самодельный браузер внутри egui.
2. **Не блокировать UI-поток**: eframe/egui рисует кадры в одном потоке; синхронный вызов
   диалога (rfd/gtk) «замораживает» окно и анимации.
3. **Деградация**: в headless/без графики или без утилит диалога — понятная ошибка + запись в
   журнал «введите путь вручную»; ручной ввод остаётся рабочим.
4. **Тестируемость**: unit/kittest-тесты не могут открывать настоящее модальное окно; backend
   должен подменяться (DI) и проверяться фейком.
5. **Без sudo и без новых системных зависимостей** (libgtk-3-dev в окружении нет; sudo запрещён).
6. Лицензии — MIT/Apache-совместимые для кода, который попадает в продукт.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы / почему нет |
|---|---|---|
| **`rfd 0.17.2`** (`xdg-portal` feature) | «Нативный» Rust-крейт, системный диалог через `xdg-desktop-portal` (D-Bus; `zbus 5.x` уже в `Cargo.lock`), MIT | +новая прямая зависимость; требует запущенного портала с KDE/GTK backend (в headless-сессии проверить нельзя); API по сути блокирующий → всё равно нужен отдельный поток; `gtk3` feature не соберётся (нет `libgtk-3-dev`); тесты — только через DI, реальный вызов в CI недоступен |
| **CLI `kdialog` / `zenity`** (выбрано) | Ноль новых cargo-зависимостей; утилиты уже установлены (`kdialog` — KDE, `zenity 4.2.1`); вид и поведение — системные; полностью тестируется подменой backend'а/скриптом; в духе ADR-0001 §3 (poppler/tesseract как внешние CLI) | Зависимость от внешних утилит (нужна деградация); парсинг stdout/exit-code; на не-KDE может использоваться zenity (GTK) |
| **`egui-file-dialog`** | Всё на Rust, не нужны внешние утилиты | Это **не системное** окно (внутри приложения), +новая зависимость; нарушает требование «системный выбор»; UX хуже нативного |
| Своё окно на egui | Нет зависимостей | То же: не системное, много кода, дублирует ОС-диалоги |

## Решение

1. **Backend — внешние CLI**: `kdialog` в KDE-сессии (`XDG_CURRENT_DESKTOP` содержит `KDE`/
   `PLASMA`), иначе `zenity`; если нет ни одного — `UnavailablePicker` с честной ошибкой.
   Вызовы:
   - `kdialog --title T --getopenfilename <start> ["Имя (*.ext *.ext)"]`;
   - `kdialog --title T --getexistingdirectory <start>`;
   - `kdialog --title T --getsavefilename <start/name> [filter]`;
   - `zenity --file-selection --title=… [--directory] [--save --confirm-overwrite]
     [--filename=<start>/] [--file-filter=Имя | *.ext]`.
   Коды возврата: `0` — выбор (путь в stdout), `1` — отмена (`Ok(None)`, не ошибка), прочее —
   деградация с текстом stderr.
2. **Фоновый поток + канал**: трейт `PickerBackend::pick()` вызывается в `std::thread::spawn`;
   результат уходит в `mpsc` и раскладывается в кадре `RdeApp::ui` (`poll_file_dialog`);
   поток вызывает `ctx.request_repaint()`. В кадре нет `block_on` и синхронных вызовов.
3. **DI для тестов**: `FileDialogService::with_backend(Arc<dyn PickerBackend>)`; в тестах —
   `test_support::FakePicker` (заданные ответы: Selected/Cancelled/Failed, запись запросов).
   `RdeApp::set_file_dialog_backend(…)`.
4. **Деградация**: нет `DISPLAY`/`WAYLAND_DISPLAY` → `Err("диалог выбора недоступен: нет
   графической сессии … — введите путь вручную")`; журнал + подпись в диалоге; поле остаётся
   редактируемым; кнопка действия не блокируется валидацией пути (ошибка видна до действия).
5. **Валидация пути** — отдельный слой (`validate_project_dir`, `validate_docx_file`,
   `validate_new_project_dir`, `validate_agent_program`, …): подсказка/ошибка под полем, кнопка
   «ОК» disabled с причиной в тултипе. Ручной ввод остаётся равноправным.
6. **Стартовый каталог**: текущее значение поля → его каталог → корень проекта; длинные пути
   обрезаются с «…» и полным путём в тултипе (`path_caption_ui`, `field_row`).
7. **Save-диалог**: API `PickKind::Save` и `CliPicker` для него реализованы и покрыты тестами;
   в текущей итерации не подключены к «Экспорт как…» (фиксированный `exports/` сохранён) —
   следующий шаг, чтобы не менять контракт сохранения документов.

## Последствия

- Новых crate-зависимостей **нет** (Cargo.toml/NOTICE не меняются).
- GUI работает без графики и в тестах: системный диалог заменяется фейком; реальное окно
  проверяется вручную на рабочем столе (`./scripts/run.sh` → «Файл → Открыть проект…»).
- Если пользователь запускает RDE в окружении без `kdialog`/`zenity`, кнопка «Проводник…»
  остаётся, но честно сообщает о недоступности; путь вводится руками (поведение до итерации).
- kdialog (GPL-2.0-or-later) и zenity (LGPL-2.1) **не входят в поставку RDE** и не линкуются,
  а вызываются как внешние программы по желанию пользователя — атрибуция в NOTICE не требуется
  (как для poppler/tesseract, см. NOTICE).
- Проверка кодов/аргументов CLI: kdialog [KDE docs](https://develop.kde.org/docs/administration/kdialog/),
  zenity 4.2.1 `--help` в окружении итерации.

## Альтернативы для следующего шага (если понадобится «нативный» вид без внешних утилит)

- `rfd` с `xdg-portal`: включается локально в `file_dialog.rs` как второй backend (тот же трейт,
  UI-код не меняется), если появится требование «без внешних CLI»; нужен запущенный портал и
  проверка на рабочем столе.
- «Открыть в файловом менеджере» уже реализовано через `xdg-open` (`RdeApp::open_in_file_manager`).
