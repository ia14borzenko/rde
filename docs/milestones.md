# Вехи RDE

Каждая веха — это проверяемое состояние продукта: тег в git + запись здесь + обновление
`.agent/plan-v01.md`. Формат: что проверено, чем подтверждено, известные ограничения, следующее.

---

## M1 — «Концепт и интеграция WordCraft» — ✅ достигнута 2026-10-24, тег `m1-concept`

**Главный вывод:** каркас RDE и интеграция WordCraft жизнеспособны; полноценный редактор
WordCraft работает внутри RDE без изменения его исходников.

### Что проверено
1. **Тулчейн и сборка WordCraft**: native-сборка v0.10.0 (commit `9130181a`) — `cargo build --locked
   --release -p wordcraft -p wordcraft-cli`, **0 errors / 0 warnings**, 3 мин 38 с; бинарь запускается,
   `wordcraft-cli commands` = 638. Подробный отчёт: `.agent/build-report-01.md` (вне репозитория продукта).
2. **Интеграция в один воркспейс**: RDE-воркспейс собирается с WordCraft как path-зависимостью —
   два Cargo-воркспейса (`exclude = ["vendor/wordcraft"]`), `[patch.crates-io] krilla` продублирован
   в корне RDE. `cargo check`/`cargo build -p rde` — зелёные.
3. **Оболочка RDE**: дерево объектов, центральные вкладки, панель агента, журнал/задачи, меню,
   статус-бар, тёмная тема; панели **скрываемые** (× в заголовке, меню «Вид»).
4. **Документ** (2 режима):
   - **Редактор WordCraft** — полный `WordApp` встроен в панель через публичный `WordApp::ui`
     (ribbon, ввод, вёрстка, undo); **исходники WordCraft не изменялись**;
   - **Предпросмотр страниц** — `.docx` читается движком (`io::open_path_in`), верстается
     (`Session::layout`) и растеризуется (`render::render_page`).
5. **Демо-документ** (теперь `demo-project/objects/documents/<id>/report.docx`) собран 55 командами
   WordCraft (заголовки, абзацы, рисунок с подписью, 1.5 интервал) — 2 страницы.
6. **Headless-скриншоты без видимых окон** (`egui_kittest` + wgpu), редактор локализуется по
   системной локали (RU: «Файл/Главная/Вставка…»).

### Артефакты
- Скриншоты: [`docs/assets/concept-v0.1.png`](assets/concept-v0.1.png) (предпросмотр, итерация 1),
  [`docs/assets/concept-v0.2.png`](assets/concept-v0.2.png) (встроенный редактор, итерация 1.1).
- Решения: [`docs/adr/0001-repo-layout-and-build.md`](adr/0001-repo-layout-and-build.md).
- Политика/журнал изменений WordCraft: [`docs/wordcraft-fork.md`](wordcraft-fork.md) — изменений нет.

### Известные ограничения (осознанно)
- Данные дерева/DAG/агента/журнала — **mock**; нет CAS/транзакций/`rde:doc`.
- **Двойной chrome** редактора: внутри панели RDE виден собственный ribbon/titlebar WordCraft.
- Нет экспортных fidelity-гейтов, шаблонов ГОСТ, MCP/ACP-агента, git-интеграции.
- Редактирование во встроенном WordCraft **не персистится в проект**: пока у RDE нет своего слоя
  сохранения (`rde:doc`/транзакции), редактор работает с временной копией документа; после выхода
  правки не сохраняются в файл проекта (осознанно — чтобы WordCraft не перезаписывал `.docx`
  в обход RDE).

### Кандидаты на следующую веху
- **M2 «Данные и связи»** — реальные объекты/дерево, store/CAS, DAG-статусы, транзакции.
- **S5 «Чистый DocView»** — нативный редактор без ribbon WordCraft (требует форк-ветки WordCraft).
- **M3 «`rde:doc` и docx-гейты»** — RDE-части пакета, обновление вставок, экспорт с проверками.

## M6 — «Живой интерфейс» — ✅ 2026-10-25 (тег `ui-live`)

**Проблема:** прототип выглядел как каркас: меню, поиск, панель «Задачи», кнопки источника и панель
агента были заглушками, объектами дерева нельзя было управлять мышью, а подписи под объектами
(«compute · выходов: 1») занимали место без пользы.

**Что сделано:**
1. **Дерево объектов**: убраны подписи под объектами (детали — в карточке-инспекторе); в заголовках
   групп счётчики; **контекстное меню по правой кнопке**: открыть/показать в инспекторе,
   обновить артефакт/связанные, оформить по ГОСТ, вставить библиографию, копия для Word, импорт
   ревью, OCR PDF, копировать id, показать каталог, переименовать, удалить (в корзину);
   ПКМ по пустому месту — «Создать объект…».
2. **Меню и диалоги**: «Новый проект» (создаёт `rde.toml` + objects/**), «Открыть проект» (по пути),
   «Настройки проекта» (имя/шаблон/пересборка → `rde.toml`), «Проверить и починить» (индекс CAS,
   статусы артефактов, документ, незавершённые транзакции, issues — отчёт в диалоге),
   «Экспорт проекта» (zip `<имя>.rde.zip`), «О прототипе» + горячие клавиши; «Правка» —
   реальные undo/redo WordCraft-сессии, «Найти в проекте»/Ctrl+F — фокус поиска, Ctrl+S — сохранить проект.
3. **Панель «Задачи»** — реальная история: транзакции хранилища и запуски `.rde/runs/*` (статус,
   время, выходы); «очистить» в журнале работает. **Панель агента** больше не притворяется чатом:
   честно «не подключён (v0.3)» + быстрые действия без агента (проверить проект, обновить артефакты,
   оформить по ГОСТ, импорт ревью).
4. **Живые элементы**: кликабельные узлы DAG (выбор/инспектор/контекст), кликабельные строки
   «Структуры» (выбор блока), счётчик вставок rde:doc, кнопки вкладки «Источник» (открыть файл,
   копировать локатор, показать в дереве), создание **документа** из диалога «+ Объект»
   (пустой `.doc.rde` через WordCraft + rde:doc).
5. **Исправлен визуальный баг**: canvas WordCraft рисовался поверх правых панелей — теперь
   ограничен видимой областью (`available_rect ∩ clip_rect`); инспектор/агент читаемы.
   Скриншоты: [`docs/assets/m6-document.png`](assets/m6-document.png), [`m6-artifacts.png`](assets/m6-artifacts.png).

**Проверка:** `cargo test -p rde-ui` — 10 UI-тестов, включая создание проекта/документа, экспорт
zip-архива, проверку проекта, контекстные действия дерева; всего в проекте **67 тестов**.
Ручная проверка: ПКМ по объектам, меню «Файл/Проект», Ctrl+F/Ctrl+S, вкладка «Задачи».

**Ограничения:** панель агента — заглушка до v0.3 (MCP/ACP); «Починить» = показать отчёт и
пересобрать индекс (автоматическое исправление не разрушающих проблем — позже); undo/redo —
в рамках сессии WordCraft; экспорт проекта — zip без истории git.

## M5 — «Источники, PDF/OCR, ревью» — ✅ 2026-10-25 (тег `m5-sources-review`)

**Что сделано:**
1. **`rde-sources`**:
   - импорт библиографии из **BibTeX / RIS / CSL-JSON** (парсеры + `import_citations`: создаёт
     объекты-источники с `[reference]`, проходит JSON Schema проекта);
   - **PDF**: текстовый слой (`pdftotext`), число страниц (`pdfinfo`), рендер страницы в PNG
     (`pdftoppm`); **OCR** (`tesseract` rus+eng) для изображений и страниц PDF;
   - **веб-архив**: `monolith`, если установлен (иначе явная ошибка — ограничение окружения).
2. **Ревью (`rde-doc`)**: чтение комментариев Word из `word/comments.xml` (автор/дата/текст),
   `import_external_review` — принять внешний `.docx` после правок в Word как новую версию,
   сохранив `rde:doc` (doc_id/шаблон/вставки), обновив `review.open`.
3. **UI**: вкладка «Источник» показывает PDF (страницы, текстовый слой, кнопка OCR; OCR-текст
   сохраняется в `ocr.txt`); у документа — число комментариев Word, «Открыть копию в Word»
   (экспорт чистого `.docx`), «Импорт ревью из exports» (самый свежий `.docx`).
4. **Демо**: добавлен PDF-источник (оформленный по ГОСТ отчёт, 2 стр.), демо-документ оформлен
   по ГОСТ с библиографией (15 блоков).

**Проверка:** `cargo test -p rde-sources -p rde-doc` — 6+7 тестов (парсеры, импорт в проект,
PDF-текст/рендер/OCR на реальном PDF, comments.xml, импорт ревью с сохранением doc_id; отсутствие
monolith). Всего в проекте **64 теста**. Скриншоты: [`docs/assets/m5-source.png`](assets/m5-source.png),
[`m5-document.png`](assets/m5-document.png).

**Ограничения:** PDF-бэкенд — poppler CLI (интеграция `pdfium-render` — следующий шаг; библиотека
уже в `refs/bin/pdfium`); OCR-качество зависит от скана (CER-гейты — v0.2); веб-архив недоступен без
`monolith`; импорт-merge ревью — v1 «принять внешнюю версию», без слияния правок по абзацам.

**Следующий шаг:** v0.3 — MCP-сервер (rmcp) и ACP-агент (DSH) по §8.7 ТЗ; параллельно — pdfium,
CER-гейты OCR, полное обновление вставок документа.

## M3 — «`rde:doc` и docx-гейты» — ✅ 2026-10-25 (тег `m3-doc`)

**Что сделано:**
1. **`rde-doc`: формат `.doc.rde`** — OOXML-пакет + RDE-часть `customXml/item1.xml` (`rde:doc`):
   `doc_id`, шаблон, `body_hash`, блоки (id/путь/тип/текст), вставки (figure/caption с
   `target=rde://artifact/...`), сводка ревью. Запись/чтение zip, `extract_docx` (чистый `.docx`
   с вычисткой RDE-частей и content-types override), детект внешних правок
   (`NotModified`/`ExternalEdit`/`MissingRdeDoc` по наличию `rde:doc` и `body_hash`).
2. **Сохранение под контролем RDE**: «Сохранить проект» пишет `.doc.rde` из редактора
   (`save_engine_document`: doc_id/шаблон/вставки сохраняются, атомарная замена пакета);
   «Экспорт .docx» — чистая копия; «Обновить документ» — перенумерация подписей «Рисунок N — …»
   через редактирующее API WordCraft + пересохранение пакета (`update_document_package`).
3. **Демо-документ мигрирован** в `demo-project/.../report.doc.rde` (12 блоков, 2 вставки,
   figure привязан к `rde://artifact/<plot-id>/out/plot.svg`), исходный `.docx` удалён (он внутри пакета).
4. **UI**: кнопки «Сохранить проект»/«Обновить документ», проверка внешних правок при старте,
   вкладка «Код документа» показывает настоящую RDE-часть `rde:doc` из `.doc.rde`.
5. **`rde-docx`: fidelity-гейты** — инвентаризация частей (sha256), WordCraft-roundtrip
   (медиа байт-в-байт, критичные части, число абзацев), **LO-оракул** (headless LibreOffice → PDF),
   JSON-отчёт. Демо: 10 частей, 0 пропавших/изменённых, медиа сохранены, 13 → 13 абзацев,
   LibreOffice 26.2 → PDF 82.8 КБ — **PASS** ([`docs/fidelity/demo-report.json`](fidelity/demo-report.json)).
6. **Сборка**: target вынесен на `/srv/yocto/rde-target` (внешний ext4), `incremental = false`,
   `debug = "line-tables-only"`, скрипты `scripts/build.sh` (guard от переполнения) и
   `scripts/clean-build.sh`; размер target 3–6 ГБ вместо 46 ГБ.

**Проверка:** `cargo test -p rde-doc -p rde-docx` — 10 тестов (XML/пакет/внешние правки/подписи/
сохранение; части/roundtrip/LO/JSON/битый файл); UI-тесты `save_project_writes_doc_rde…`,
`structure_parser_reads_doc_rde_package`; демо-гейт PASS.
Скриншоты: [`docs/assets/m3-document.png`](assets/m3-document.png), [`m3-code.png`](assets/m3-code.png).

**Ограничения:** вставки обновляются пока перенумерацией подписей (полное обновление содержимого
из артефактов — M4); комментарии Word в `rde:doc` ещё не импортируются (M5); PDF-экспорт — через
LO-оракул, не встроенный рендерер.

**Следующий шаг:** M4 — шаблоны ГОСТ 7.32-2017, правила оформления, библиография из источников.

## M2.3 — «Запуск и обновление» — ✅ 2026-10-25 (тег `m2.3-run-dag`)

**Что сделано:**
1. **`rde-run`** — реальное исполнение скриптов артефактов: изолированный workdir
   `.rde/runs/<run_id>/work`, копирование скрипта и входов в `inputs/`, отдельная процессная группа,
   stdout/stderr в логи, `run.json` (provenance), таймаут и отмена (SIGKILL группы без потомков),
   проверка объявленных выходов. 7 тестов (успех/логи, входы, nonzero exit, нет выхода, таймаут,
   отмена, нет скрипта).
2. **Транзакции с payload** (`rde-store`): `begin_tx_with(note, data)`, payload переживает
   переоткрытие и пересборку индекса.
3. **`rde-dag`** — `act_key` из `in_hash`/`script_hash`/`params_hash`/`env_hash`; `in_hash` из
   `hashed`-групп (файлы/выходы артефактов/источники); ledger из committed-транзакций
   (`kind="dag-update"`); статусы из хешей: «актуален / устарел (изменились входы, скрипт, параметры;
   выход изменён вручную; выходы удалены) / не запускался»; топопорядок; `update()` с транзакцией на
   артефакт (выходы → CAS, дерево, ledger), прогрессивное обновление, ошибка не портит ledger.
   5 тестов: цепочка demo `stats → plot`, правка входа → пересчёт обоих, падение скрипта,
   ручная правка/удаление выхода, топопорядок.
4. **UI**: статусы артефактов и DAG пересчитываются из `rde-dag` при старте и после обновления;
   кнопка **«Обновить всё»** и **«Обновить связанные»** (в DAG-вкладке — выбранный артефакт +
   зависимые) реально запускают обновление; журнал получает строки запусков с act_key.
   Скриншот: [`docs/assets/m2.3-artifacts.png`](assets/m2.3-artifacts.png).

**Проверка:** `cargo test -p rde-run -p rde-dag` (12 тестов) и UI-тест
`dag_update_from_ui_runs_real_artifacts`; на живом демо-проекте: первый
`cargo run -p rde-dag --example update-demo` — 2 запуска, второй — 0 запусков, CAS 3 блоба/3 дерева/2 транзакции.

## M2.2 — «Хранилище и хеши» — ✅ 2026-10-24 (тег `m2.2-store`)

**M2.2a — `rde-hash` (готово):**
- SHA-256 содержимого; `tree_hash`/`out_hash` (Merkle-дерево: путь, режим, блоб);
  `group_hash` → `in_hash` (только `hashed`-группы); `script_hash`, `params_hash` (канонический JSON),
  `env_hash`, `act_key` — по формулам `tz-02` §7.2.
- Инженерное уточнение: все компоненты хешируются **length-prefixed** (домен + длина + байты), чтобы
  исключить неоднозначность склейки; зафиксировано в doc-комментарии крейта.
- 6 тестов: канонизация JSON, независимость от порядка (дерево/группы/`in_hash`), чувствительность
  `act_key` к каждому компоненту, `ref`-группы не влияют на `in_hash`, golden-векторы формата.
- Проверка: `cargo test -p rde-hash`; пример с векторами: `cargo run -p rde-hash --example vectors`.

**M2.2b — `rde-store` (готово):**
- CAS `.rde/cas/sha256/ab/cd/<hash>` (immutable, дедупликация), деревья версий `trees/<hash>.json`,
  журнал транзакций `updates/<txid>.json` (prepared/committed/failed), каталог `.rde/{snapshots,trash}`
  под следующие вехи.
- **Атомарная запись** `temp + fsync + rename + fsync(dir)`; при открытии удаляются недописанные
  temp-файлы, оставшиеся после kill -9.
- **Ребилдируемый индекс** SQLite (`index.db`): blobs/trees/txs; `Store::open` подтягивает/пересобирает
  индекс из файлов; `rebuild_index()` проверяет целостность (имя блоба == sha256 содержимого,
  tree_hash дерева, журнал) и сообщает о повреждениях.
- **Журнал транзакций**: `begin_tx`/`commit_tx`/`fail_tx`; при открытии проекта незавершённые
  `prepared`-транзакции попадают в `RecoveryReport` (диагностика «Проверить проект»).
- **kill -9-харнесс**: дочерний процесс пишет блобы, родитель убивает SIGKILL, после чего
  `Store::open` + `rebuild_index` подтверждают целостность всех блобов.
- Проверка: `cargo test -p rde-store` — 5 тестов (CAS/дедуп/раскладка, деревья, журнал/восстановление,
  пересборка/порча, kill -9); демо: `cargo run -p rde-store --example demo`.

**Следующий шаг (M2.3):** подключить `act_key`/`out_hash` к статусам проекта вместо эвристик;
`rde-run` (запуск скриптов артефактов через python/uv) + DAG-транзакции/откат через store; затем
«Обновить связанные» в UI — рабочая кнопка.

## P1 — «Нормативные исправления артефактов» — ✅ достигнута 2026-10-25, тег `p1-artifacts`

**Главный вывод:** артефактная часть приведена к нормативной модели §7 ТЗ-02 без залезания в
чужие подсистемы (store/run/env/doc/vcs — это P2–P5, см. ADR-0002). Каждый пункт подтверждён
тестом, хеш-формат зафиксирован golden-векторами.

### Что проверено
1. **`hashed`/`ref`-семантика** (§7.3 п.1/п.4): `Project::dag_edges` и топосортировка используют
   только `hashed`-группы; `ref`-рёбра не дают каскада и не участвуют в порядке (тесты:
   `ref_groups_do_not_create_dag_edges`, `ref_edge_does_not_cascade_and_ref_cycle_is_not_a_dag_cycle`).
2. **Циклы** (§7.3 п.3): DFS-раскраска при загрузке проекта с цепочкой («A → B → A»), устойчивый
   топопорядок (Кан); property-тест на 30 случайных графах с гарантированным циклом.
3. **Формулы §7.2**: `canonical_json` — RFC 8785 (JCS: ключи по UTF-16, ECMAScript-числа),
   `script_hash = H(runtime|entry|H(bytes)|sorted[extra_script_files])`, `act_key` включает
   `schema_version`; golden-векторы обновлены осознанно. Property-тесты: идемпотентность JCS,
   round-trip f64, перестановки Merkle-дерева, чувствительность `act_key`, ref-группы в `in_hash`.
4. **Причины устаревания по компонентам** (§7.3 п.2): `StaleReason::{InputsChanged, ScriptChanged,
   ParamsChanged, EnvChanged, SchemaChanged, OutputsMissing, OutputsModified, StateIncomplete}`;
   состояние хранит компоненты `act_key` (старые записи ledger честно помечаются `StateIncomplete`).
5. **Входы**: glob-селекторы (`out/*.csv`, `out/**/*.dat`) с единой семантикой загрузки/DAG/запуска;
   входы-константы `{ constants = "<id>", selector = "R_n" }` материализуются в
   `inputs/constants.json`/`inputs/constant-<имя>.json`, их хеш входит в `in_hash` (end-to-end тесты).
6. **Обновление**: «обновить артефакт» — только цель, принудительно (`force`); «обновить связанные» —
   цель + транзитивно зависимые; `dependents_closure` — публичный API для UI/MCP.
7. **`out_hash` в манифесте** (R-VCS-02, §7.3 п.10): после успешного обновления пишется в
   `artifact.toml` без потери комментариев (идентичность выходов для git-диффа).
8. **Scaffold артефакта** (R-ART-01): при создании — `readme.md`, `.gitignore` (выходы не коммитятся),
   `out/.gitignore`; `rde-run` умеет сгенерированные входы (`InputFile::from_bytes`).

## P2 — «Транзакционное ядро store» — ✅ достигнута 2026-10-25, тег `p2-store`

**Главный вывод:** обновления артефактов стали настоящими транзакциями с O(1)-откатом:
store владеет корнями/снапшотами/GC, dag оркестрирует «пачку» и материализацию, UI даёт кнопку
«Откатить». Дублирования логики между слоями нет (ADR-0002 соблюдён).

### Что проверено
1. **Корни и смена `current`** (§7.3 п.7): `current.toml` (имя → `tree_hash`), транзакция с новыми
   корнями пишет снапшот `snapshots/<txid>.json` → атомарно переключает `current.toml` → журнал
   `committed`; восстановление после kill -9 на любом шаге (prepared+снапшот+current==new →
   транзакция дозавершается, иначе помечается failed).
2. **Откат O(1)** (R-ART-05): `Store::rollback(txid)` / `rollback_latest()` переключают `current.toml`
   на предыдущие корни; откат сам является транзакцией (его тоже можно откатить). `rde_dag::rollback`
   дополнительно материализует прежние выходы из CAS в каталоги артефактов, возвращает ledger-состояния
   (`dag-update`-payload) и снимает `out_hash` при откате к «ещё не запускался». Входные файлы проекта
   откат не трогает — статус честно показывает «изменились входы».
3. **Транзакция «пачки»**: `UpdateOptions { batch: true }` — все артефакты обновления фиксируются
   одной транзакцией (атомарные корни); `batch: false` — по транзакции на артефакт (гранулярный откат).
   UI: «Обновить всё»/«связанные» — пачка, «обновить артефакт» — своя транзакция.
4. **GC/pins** (§7.3 п.8, R-ART-11): mark-and-sweep от `current` корней + окна отката (N транзакций
   и/или дней) + pins; отчёт до/после, `dry_run`; pins не удаляются; failed-транзакции старше окна
   прунятся; индекс пересобирается из файлов.
5. **zstd в CAS** (§8.4): крупные сжимаемые блобы хранятся с маркером `RDEZ`, имя файла — sha256
   несжатых байт (адресация/дедупликация не меняются); чтение/проверка/индекс понимают сжатие.
6. **Блокировка писателя**: `.rde/lock` с pid и liveness-проверкой (Linux `/proc`); между процессами —
   эксклюзивно, внутри процесса — общий реестр (UI/тесты/инструменты); устаревший lock снимается.
7. **UI**: панель «Задачи» показывает транзакции обновлений с кнопкой «Откатить» и пометкой «откачено».

### Подтверждение
- Тесты: **100** (было 90), из них новые: 5 store (`tests/p2.rs` — zstd/rollback/recovery/GC/lock),
  4 dag (batch-транзакция, откат выходов+ledger, откат к «не запускался», GC после обновлений),
  1 UI (откат из панели «Задачи»); `cargo test --workspace` зелёный.
- Скриншот: [`docs/assets/p2-tasks-rollback.png`](assets/p2-tasks-rollback.png) — панель «Задачи»
  с транзакцией и кнопкой «Откатить».

### Известные ограничения (уходят в следующие шаги)
- Окно отката настраивается API (`GcOptions`), но не в UI-настройках (P5).
- GC не прунит успешные старые транзакции (журнал маленький; компакция ledger — вместе с P3/P5).
- `document/<id>` корни и транзакция обновления документа — P4 (rde-doc).
- Окружения/`env_hash` digest, trust/network, read-only входы, SIGTERM→grace — P3 (rde-env/rde-run).

### Следующий шаг
**P3 — запуск/окружения/безопасность/provenance:** `rde-env` (uv/`rde.lock`/digests), trust-consent,

## P3 — «Запуск, окружения, безопасность, provenance» — ✅ достигнута 2026-10-25, тег `p3-run-env`

**Главный вывод:** запуск артефактов стал воспроизводимым и подотчётным: окружение разрешается
отдельным слоем `rde-env` и входит в `env_hash`, запуск требует согласия, сеть по умолчанию
запрещена, лишние файлы — ошибка, каждый запуск оставляет SLSA-подобный `provenance.json`.

### Что проверено
1. **`rde-env` (новый крейт)**: разрешение окружений (`python` — `uv venv .venv` + `uv.lock`,
   `node` — `pnpm-lock.yaml`, `r` — `pixi.lock`, `shell`), версии интерпретаторов/менеджеров,
   digest записи (JCS) → вход `env_hash` (§7.2); `rde.lock` (TOML) фиксирует окружение в git.
   Смена режима (`project`/`system`) или объявленных `vars` меняет `env_hash` → статус
   «изменилось окружение» (тест dag).
2. **rde-run hardening** (R-RUN-04/05/06/08):
   - согласие «проект доверенный» (`trusted` в `rde.toml`): без него запуск отклоняется;
   - сеть по умолчанию запрещена best-effort (blackhole-прокси + `RDE_NETWORK=deny`), включается
     декларативно (`network_allow`); в provenance честно фиксируется «best-effort»;
   - входы и скрипт материализуются только для чтения (`chmod 0444`);
   - файлы вне объявленных `outputs` — ошибка с перечнем (кроме `__pycache__`/`.rde*`);
   - отмена/таймаут: SIGTERM → grace 2 с → SIGKILL процессной группы;
   - интерпретатор берётся из разрешённого окружения (`.venv/bin/python`), а не из PATH;
   - `runDetails` provenance: script_hash, env_lock_digest, platform, network/trusted, exit_code,
     digest логов, время, extra_files;
   - логи: чтение с байтового смещения, поиск, ретенция запусков (`prune_runs`).
3. **Provenance** (R-ART-08): `runs/<run_id>/provenance.json` — SLSA-подобный statement:
   `subject` = out_hash, `externalParameters` (артефакт, act_key, in/script/params/env hash, params,
   инициатор), `resolvedDependencies` (`rde://artifact/<id>@<out_hash>`, файлы/заметки/источники/
   константы), `runDetails`. Пишется для успешных и неуспешных запусков (с `error`).
4. **UI**: диалог согласия перед первым запуском («Доверяю проекту и запустить» → `trusted = true`);
   фоновое обновление (UI не блокируется) с индикатором и кнопкой «Отменить»; в инспекторе —
   режим окружения, `env digest` (сверка с `rde.lock`), политика сети, согласие, кнопка
   «копировать путь provenance».

## P6 — «Доработки по обратной связи v0.1» — ✅ достигнута 2026-10-25, тег `p6-feedback`

**Контекст:** просмотр демо-проекта выявил UX/функциональные дефекты; все четыре пункта закрыты.

1. **Рисунок из артефакта не отображался (серый прямоугольник).** Причина: DocView WordCraft
   рендерит растровые изображения и WMF/EMF, но не SVG (fallback — серая заглушка). Решение:
   `rde-doc::rasterize_svg` (resvg, MPL-2.0) — SVG-выход артефакта растеризуется в PNG при
   вставке/обновлении рисунка; источник истины (`target` в rde:doc) остаётся SVG-выходом.
   Демо-документ пересобран: `word/media/rde-figure-2.png`, WordCraft-модель видит оба рисунка.
2. **Вставка «Среднее значение x1» имела чужой вид/рамку.**
   - **Стиль:** вставка теперь получает стиль обычного текста текущего шаблона (`w:pStyle` из
     `styles.xml`, по умолчанию — стиль абзаца документа, в демо `Normal`); стиль хранится в
     `rde:doc` и **редактируется пользователем** (диалог вставки + таблица вставок во вкладке
     «Структура» с применением).

     `int`, `dec:N`, `sci:N` (стандартный вид `m·10^e`), `percent:N`; формат — поле вставки,

     редактируется как обычный текст.
3. **Кнопка «Открыть» в инспекторе артефакта ничего не делала.** Теперь «Открыть» артефакт =
