Спайк отвечает на вопросы §2 ТЗ сессии: можно ли на этом стенде дать владельцу **настоящий визуальный
LaTeX-редактор уровня MathType** (визуальные структуры/палитры/клавиатура, LaTeX как источник истины)
и как встраивать его окно в RDE, не теряя офлайн-поставку, лицензии и Word-совместимость.

---

## 1. Ключевое ограничение стенда: встроенный webview невозможен

| Проверка | Результат (2026-10-31) |
|---|---|
| `pkg-config --modversion webkit2gtk-4.1` / `webkit2gtk-4.0` / `gtk+-3.0` | **не найдено** (dev-файлов `.pc` нет) |
| `dpkg -l \| grep webkit2gtk` | рантайм есть: `libwebkit2gtk-4.1-0` 2.52.6, `gir1.2-webkit2-4.1`; **`libwebkit2gtk-4.1-dev` не установлен** |
| `ldconfig -p \| grep webkit2gtk` | `libwebkit2gtk-4.1.so.0` присутствует (рантайм) |
| `apt-cache policy libwebkit2gtk-4.1-dev` | кандидат 2.52.6 есть, но установка требует `sudo` (запрещено ТЗ) |
| `sudo` | недоступен для агента (и запрещён правилами итерации) |
| Дисплей | `DISPLAY`/`WAYLAND_DISPLAY` пусты; Xvfb нет — GUI-проверка руками/скриншоты возможны только headless |
| Chrome/Chromium | **google-chrome 155.0.8059.39** установлен; `--headless=new` работает |
| node | v22.22.1 (есть `WebSocket` — CDP-драйвер для headless-проверки без зависимостей) |

Вывод: `wry`/`webkit2gtk`-крейты **не собираются** (нет `webkit2gtk-4.1.pc` и GTK-заголовков), а
ставить системные dev-пакеты без `sudo` нельзя. Вариант «распаковать `.deb` в локальный sysroot» спайк
не рассматривает как продуктовый: воспроизводимость сборки ломается, правило итерации — «системные
пакеты не ставить». При этом браузер уже есть — и владелец **явно разрешил webview и отдельное окно
на рабочем столе** («как MathType»), поэтому выбран путь «отдельное окно браузера в режиме
приложения» (`--app=`): это webview-класс UX без сборки webview-стека и без `sudo`.

## 4. SVG-вставка: что известно и что проверено LO-оракулом

P0/P5 уже умели вставлять SVG (`render_mode=svg`, `asvg:svgBlip` + PNG-fallback). В P6 проверялся
**baseline** — «формула в строке/номер справа на той же базовой линии».

Стенд-эксперимент (LO 26.2.6.3, искусственный `.docx` с inline-PNG 20 pt и текстом 11 pt; правила
измерения — в `docs/fidelity/p23-formula-editor-window.md`):

* **inline-картинка в WordprocessingML садится НИЗОМ на базовую линию текста** (измерено: низ
  картинки 76,60 pt, базовая линия текста 76,32 pt — расхождение в пределах растеризации 0,28 pt).
  Следствие: SVG-картинка inline-формулы **не может** сохранить математический baseline — нижние
  индексы/дроби всегда «приподняты» на величину `descent`. Это ограничение OOXML, а не реализации
  (LO и WordCraft ведут себя одинаково: `layout/para.rs`: «A picture sits on the baseline of its run»).
* `<w:position>` (raise) на run с картинкой **не сдвигает картинку** в LO (проверено: положение
  квадрата не изменилось) — «опустить» inline-картинку под базовую линию нельзя.
* **Вывод для продукта:** inline-формулы по умолчанию остаются **OMML** (нативная математика с
  точным baseline); SVG — основной режим для **display**-формул. Для display+SVG номер `(N)`
  поднимается через `<w:position>` (обычный текст LO/Word поднимают; WordCraft читает/пишет
  `w:position` и применяет `CharProps.position`) на `descent + отступ кропа` — базовая линия номера
  совпадает с базовой линией формулы (проверено скриншотом документа: `gui-p23-formula-svg-document.png`).

## 5. Безопасность окна/моста (заложено в POC и продукт)

* сервер моста слушает **только** `127.0.0.1`, случайный порт; bind loopback;
* `Host` обязан быть loopback-именем (защита от DNS-rebinding) — чужой Host → 403;
* API-маршруты требуют одноразовый токен 16 байт CSPRNG в query, сравнение за постоянное время;
* тело ≤ 512 КиБ, заголовки ≤ 32 КиБ, таймауты 3 с; ответы `nosniff`, `no-store`;
* страница отдаётся с CSP `default-src 'self'; connect-src 'self'; …` — только свои ассеты;
* Chrome запускается с `--disable-background-networking --disable-component-update --disable-sync`
  и изолированным профилем; LaTeX — данные, из страницы не исполняется код RDE; JS-мост ограничен
  тремя операциями (state/apply/cancel/prefs).

## 7. Риски и деградация

1. **Нет браузера** — окно не открывается; панель «Формула» остаётся с LaTeX-полем и предпросмотром
   (понятное сообщение). На Linux fallback — браузер по умолчанию (`xdg-open`), на Windows — Edge
   (входит в ОС), на macOS — Chrome/Edge/Chromium или `open`.
2. **Браузер не умеет `--app=`** (Firefox) — fallback в обычную вкладку; окно закрывает пользователь,
   RDE получает apply/cancel по мосту.
3. **Windows/Wayland** — пути запуска заложены, но вручную не проверялись (`unverified`), на стенде
   нет графической сессии; headless-проверка — Chrome на Linux.
4. **Визуальный стиль окна (KaTeX) ≠ документ (STIX)** — окно показывает TeX-типографику; документ
   остаётся WordCraft/STIX. Это осознанное отличие (MathType тоже не рендерит документный шрифт).
5. **Word** — SVG+номер проверены LO-оракулом; Word на стенде нет (`unverified`), `svgBlip`-часть
   пишется прежним (проверенным в P0) способом.
6. **Внешний процесс/память** — окно закрывается → процесс браузера гасится (kill process group),
   мост останавливается; при падении браузера пользователь видит «Отмена» и не теряет источник.

## 8. Вывод (Research Gate)

1. **Выбран путь**: MathLive 0.111.1 (MIT, офлайн-бандл в репозитории) в отдельном окне браузера в
   режиме приложения; JS↔Rust мост на loopback; LaTeX — источник истины; SVG-рендер и вставки —
   внутри RDE прежним конвейером (ADR-0018/0020), с выравниванием номера по метрикам вёрстки.
2. Встроенный `wry` на стенде невозможен (нет dev-заголовков, `sudo` запрещён) — зафиксировано как
   ограничение среды; при появлении dev-пакетов окно можно перевести на встроенный webview (страница
   и мост уже отделены от способа показа — `rde-formula-editor` не зависит от UI RDE).
3. Паритет MathType достижим сразу (MathLive даёт структуры/палитры/клавиатуру/undo/LaTeX I/O);
   отложенное — матричный тулбар/кастомизация палитр под ГОСТ (P2 бэклог), Word-проверка.
4. Решение и план — [ADR-0022](../adr/0022-latex-editor-window.md).
